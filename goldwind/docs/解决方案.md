# 解决方案：面向企业的多智能体协作，在运行时上把业务自动做起来

## ——金风科技标准知识库的业务化落地（POC 方案底稿）

本方案的主叙事只有一句：**面向企业的多智能体协作，在运行时上把业务自动做起来。** 落到金风科技，这句话要解决的不是“再建一个标准文档库”，而是让企标、国标、行标、团标、IEC/IEA 等标准知识，从“存在系统里”变成“在认证、投标、供应链准入、现场作业这些任务发生时，被岗位型 Agent 取得到、引得准、用得上”。多角色协作完成“找依据、做比对、出草稿、标风险”，人保留“定结论、签字、放行、对外”。

> **边界声明（先读）**
>
> - 截至本文，**金风科技不是 Agent Forge 的签约客户，双方未签约、未上线**。本文是基于公开信息与上游《痛点分析》形成的方案假设，不构成合作陈述、交付承诺或效果承诺。
> - 本文只沿用上游痛点分析的判定与优先级，**不自行放宽自动化边界**；P2、P3、P6 的“痛点”属性本身仍需访谈验证，文中按“假设 + 待核”表述。
> - 本文不声称 Agent Forge 具备未列出的连接器、自动签字、自动准入或 100% 准确率；凡涉及产品能力与系统集成，均标注“需实施评估”。
> - 对外使用前须由人工核对公开信息与证据级别；协作内不自动对外发布。

## 一、先回答三个问题：谁协作、谁审批、怎么验收

### 1.1 在该企业，哪些业务由哪些岗位型 Agent 协作完成

标准知识本身不产生业务结果，必须“长”在岗位上。建议把标准能力配置成六类岗位型 Agent，按业务场景组队：

| 业务场景                                           | 岗位型 Agent（角色与职责）                                                                                                                                                                                                                                                         | 协作模式                                                                                      | 人工审批/签字                                                                                                                    | 交付物与验收口径                                                                                                                   |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **认证符合性应答**（首选 POC）                     | 任务解析 Agent：把认证规则/测试大纲拆成条款级清单；证据匹配 Agent：在“标准—机型—市场—认证体系”映射下找证书、报告、测试记录；缺口 Agent：列缺证据、偏离候选、待澄清项；撰写 Agent：逐条起草并带引用；引用校核 Agent：独立复核版本、适用范围、型号与数字一致性；汇总 Agent：收口成包 | **Supervisor + Pipeline 混合**：解析与汇总由 Supervisor 调度，匹配→缺口→撰写→校核走固定流水线 | 技术负责人逐条确认适用性与技术结论；商务确认报价/交付/承诺；法务审法律条款；**授权签字人签字提交**。Agent 无签字、盖章、提交权限 | 条款级应答初稿、偏离表草稿、证据索引、缺口清单、引用溯源表。验收看：引用可追溯率、抽检错引数、条款覆盖率、单包工时、人工一次采纳率 |
| **投标技术应答**（POC-1 的第二段，待 Q4 验证后扩） | 在认证应答角色上增加“招标文件解析”和“历史标书复用”能力；商务/法务角色前置参与                                                                                                                                                                                                      | Pipeline 为主，Supervisor 处理跨章节冲突                                                      | 技术、商务、法务**三签**；报价、交付承诺、合同条款由人定稿                                                                       | 技术偏离表草稿、符合性声明草稿、逐条应答。验收同上，另看“偏离项漏报数”                                                             |
| **供应商准入证据包**（POC-2）                      | 证书识别 Agent：OCR + 有效期/认证范围/标准依据结构化；条款比对 Agent：按品类规则逐条比对；证据缺口 Agent：缺件、过期、范围不符；风险摘要 Agent：红黄灯与复核点；汇总 Agent：出证据包                                                                                               | **Pipeline**：固定顺序、每步可回放，避免多角色自由对话导致责任漂移                            | 采购经办核原件；**采购 + 质量会签人做准入结论**；过期、范围不符、无法识别三类强制人工复核。Agent 不写回准入结论                  | 证据包、红黄灯、有效期日历、缺口清单、复核建议。验收看：关键字段抽检准确率、过期证书漏检数（硬指标 0）、证据可追溯率、单家工时     |
| **运维作业标准注入**（POC-3，第二期/备选）         | 变更解析 Agent：读标准换版 diff；影响载体识别 Agent：反查手册章节、巡检判据、课程、合同条款；改稿建议 Agent：出 diff 建议；一致性校核 Agent：查漏改/错改；汇总 Agent：出影响面报告                                                                                                 | **Pipeline + Supervisor 异常路由**：主链路固定，遇到跨系统冲突升级给人                        | 专业工程师签认技术内容；作业主管/培训主管签认发布；**发布仍走原手册/培训/巡检系统流程**                                          | 影响面清单、修订建议稿、校核报告、待确认清单。验收看：影响载体召回率、建议稿采纳率、换版排查周期、错改/漏改数                      |
| **条款级检索/岗位问答**（共用底座，不单独做 POC）  | 检索 Agent + 引用校核 Agent 双角色即可；不铺多智能体                                                                                                                                                                                                                               | 轻量 Pipeline                                                                                 | 工程师对“引用是否适用”自行确认；高风险问题转专家                                                                                 | 带“标准号 + 条款号 + 版本 + 适用范围”的答案；无来源则拒答                                                                          |
| **培训问答/专家经验复用**（暂不做 POC）            | 单点 RAG 足够，不上多智能体                                                                                                                                                                                                                                                        | 单 Agent                                                                                      | 专家仍对疑难判断负责                                                                                                             | 只做试水，不包装成“业务自动化”                                                                                                     |

**一句话概括**：自动化完成的不是“标准化部门”这个职能，而是认证/投标应答、供应商准入证据整理、作业文件同步这三类**重复、规则明确、可抽样验收**的工作；标准解释权、符合性结论、准入结论、签字放行仍然在人。

### 1.2 谁审批：四类动作不交给 Agent

沿用上游判定，AI 做到“找依据、做比对、出草稿、标风险”；人保留“定结论、签字、放行、对外”四类动作。具体审批矩阵：

| 决策点                           | 审批人/签字人         | Agent 能做什么                         | Agent 不能做什么             |
| -------------------------------- | --------------------- | -------------------------------------- | ---------------------------- |
| 标准条款是否适用于某机型/市场    | 技术负责人/专业工程师 | 检索、比对、标注版本与适用范围、列冲突 | 代替工程师判定“符合”         |
| 认证/检测报告最终签字盖章        | 授权签字人            | 组织证据、生成初稿、做一致性校核       | 签字、盖章、修改原始记录     |
| 投标报价、交付承诺、合同法律条款 | 商务负责人 + 法务     | 生成偏离表草稿、提示风险条款           | 定价、承诺交付、终稿法律条款 |
| 供应商准入通过/不通过            | 采购 + 质量会签人     | 出证据包、红黄灯、缺口清单             | 自动准入、写回准入结论       |
| 设计红线符合性                   | 专业工程师            | 找条款、列证据、标不确定               | 判定符合/不符合              |
| 安全类定级与作业许可             | 安全负责人            | 提供标准依据与检查项                   | 签发许可、绕过规程           |
| 作业文件/课程/巡检规则发布       | 作业主管/培训主管     | 出修订建议稿、做一致性校核             | 直接发布、直接写回           |
| 对外披露/ESG 口径                | 品牌/IR/法务          | 不做                                   | 生成对外定稿                 |

### 1.3 怎么验收：三层验收，不以 Demo 效果替代生产验收

1. **业务验收**：以客户基线为对照，抽样复核。每条 POC 在启动第 1 周先测基线（工时、返工、错引、漏项），验收时用同一口径复测；没有基线的指标不作为承诺。
2. **技术验收**：引用回链率 100%（每条结论可回到标准号、条款号、版本、证据文件；这是**流程门槛**——无来源必须标“无来源”并阻断，不是模型准确率承诺）；权限与数据隔离通过越权测试；审计记录完整可回放；评测集（建议 50–100 条）准确率达标。
3. **治理验收**：审批节点不可绕过；Agent 无签字/提交/写回权限；熔断可触发；异常升级有人接手；所有会话可检索、可导出。

**三条硬规则**（贯穿全部 POC）：

- **无来源不回答**：没有可回链的条款或证据，必须显式说“无来源/待核”，不得补写。
- **无审批不提交**：对外文件、准入结论、系统写回，一律经人工审批。
- **无授权不入库**：标准文本、企标、历史标书、供应商材料，按版权与数据权限确认后再入库。

## 二、客户问题：不缺标准，缺任务现场的定位与追溯

上游事实基线（详见《痛点分析》§1，来源编号 F/S 可在画像中核对）：

- 国内标准 699 项（已发布 592 项）、IEC 34 项、IEA 课题 21 项；国内标准三年增长约六成（F8、F9）。
- 2026 年上半年获认证证书 92 张（国内 38、国际 54）（F17）。
- 全球运维服务量超 113GW、运维团队 4,000+ 人（F4）；内训师 253 人、成熟课程 304 项（F26）。
- 标准已进入设计红线、供应商品类规则、合同准则、手册、巡检项、课程六类载体（F15、F19、F20、F23、F24、F26），但“标准—条款—机型—市场—载体”的公开索引缺失（G1、G3、G4）。

由此形成六条痛点，方案只回应其中三条高优先级切口，其余作为底座或暂不做：

| 痛点                            | 置信度             | 本方案回应                                          | 是否单独立项      |
| ------------------------------- | ------------------ | --------------------------------------------------- | ----------------- |
| P5 认证/投标符合性应答重复劳动  | 认证侧高、投标侧低 | **POC-1**：多角色协作出应答初稿与偏离表草稿，人三签 | 是（首选）        |
| P4 供应链准入人工比对证书与条款 | 高                 | **POC-2**：证据包 + 红黄灯，不做准入结论            | 是（次选）        |
| P3 手册/课程/巡检项与标准不同步 | 中                 | **POC-3**：影响面清单 + 修订建议稿，第二期          | 是（备选/第二期） |
| P2 条款级检索缺失               | 中                 | 作为 POC-1/2/3 的共用底座，不单独做 POC             | 否                |
| P1 版本与影响面台账             | 高                 | 作为底座随 P2 一起交付，不单独竞争 POC              | 否                |
| P6 专家知识复用不足             | 中低               | 单点 RAG 试水，不做多智能体 POC                     | 否                |

> 说明：P2、P3、P6 的“痛点”属性来自画像分析判断，须访谈确认；P5 投标侧证据最弱（画像标“弱”、G6 空缺），因此在 Q4 完成前，**POC-1 只承诺认证侧 + 1 个投标样本验证，不承诺投标全流程**。

## 三、标准知识怎么“进来”：先做底座，再做场景

标准知识库不是把 PDF 全量丢进向量库。要让 Agent 在任务现场“引得准”，至少要过五道工序：**采集与授权 → 解析与条款切分 → 元数据标注 → 映射表建立 → 抽检发布**。

```
标准源                     知识底座                          Agent 使用
国标/行标/团标/企标  ──►  条款切片 + 版本台账 + 适用范围映射  ──►  检索/比对/引用
IEC/IEA/认证规则          （标准—机型—市场—认证体系—载体）        （MCP / Skill）
客户文档（手册/标书/证书）
```

### 3.1 来源分层与授权

| 来源                         | 获取方式          | 入库前必须确认                     | 备注                                     |
| ---------------------------- | ----------------- | ---------------------------------- | ---------------------------------------- |
| 国家标准、行业标准、团体标准 | 公开/采购         | 版本、实施日期、是否被替代         | 公开可查不等于可自由复制，按授权范围使用 |
| IEC/IEA 标准与合格评定规则   | 正式订阅/成员渠道 | 版权许可、内部使用范围             | 不得整篇外传或用于对外产品               |
| 企业标准（Q/GW）             | 客户内部授权      | 密级、可访问人群、是否允许入检索库 | 最贴近作业，也最敏感                     |
| 手册、标书、证书、审核记录   | 客户系统导出      | 数据权限、脱敏、留存期限           | 按项目隔离，不跨项目混用                 |

### 3.2 条款级结构（引用的最小单位）

每条入库内容至少带六个字段：**标准号、标准名称、条款号、版本（含发布/实施日期）、适用范围（机型/市场/认证体系）、原文片段**。引用时必须是“四要素”齐全：**标准号 + 条款号 + 版本 + 适用范围**，缺一不可。

### 3.3 三张关键映射表

1. **标准—机型—市场—认证体系**：回答“这个机型卖到这个市场，该用哪版标准、走哪套认证”。
2. **标准—载体**：回答“这条条款被哪些手册章节、合同条款、课程、巡检项引用”。
3. **版本—替代关系**：回答“新版生效后，旧版何时失效、哪些引用要改”。

这三张表在公开信息中均无证据（G2、G3、G4），**POC 第一周就要确认是否已存在**：若已有成熟系统，方案从“新建”改为“接入”；若没有，先建最小可用版本，不追求全量覆盖。

### 3.4 知识底座的产品形态

- **优先接入客户既有标准库/文档系统**：通过 MCP/Skill/API 读取，避免重复建设；具体接口、权限、写回能力需实施评估。
- **若采用 Agent Forge Knowledge（AFK）承载标准语料**：按 AFK 口径规划，但其版本管理、文档级权限、引用回链能力需在实施评估中逐项确认，本文不预设未列出的功能。
- **不建议**首期自建“大而全”的标准管理平台；POC 阶段只建“够用”的条款索引与映射，验证业务价值后再扩。

## 四、三个业务自动化 POC 切口

> 三个切口严格对应上游优先级与画像 §4.3 三个抓手，不新增方向。POC-1 首选，POC-2 次选，POC-3 第二期/备选。

### 4.1 POC-1：认证/投标的标准符合性应答（首选）

**场景**

认证侧：新机型、新市场或标准换版时，依认证规则组织“标准→测试大纲→报告→证书”的符合性证据包。投标侧：按招标文件编制技术偏离表、符合性声明和逐条应答。两者共性是高价值、高频、高度模板化，且逐条可抽样验收。

**输入**

- 标准条款库（含版本、生效日、适用范围）
- 认证规则/招标文件/技术规范书
- 机型配置、技术参数、历史证书与测试报告
- 历史应答文件（脱敏）、专家名单与分工
- 客户既有的模板、偏离表格式、术语表

**多智能体分工**

| 角色                              | 职责                                                                      | 关键约束                           |
| --------------------------------- | ------------------------------------------------------------------------- | ---------------------------------- |
| 任务解析 Agent（Supervisor 入口） | 把认证规则/招标文件拆成条款级 checklist，标注“必须响应/可偏离/需澄清”     | 不遗漏条款；拆不准的标“待人工确认” |
| 证据匹配 Agent                    | 在映射表下检索证书、报告、测试记录，输出“有证据/证据过期/证据不足/无证据” | 只认有效期内、范围匹配的证据       |
| 缺口与偏离 Agent                  | 汇总缺口、偏离候选、需澄清问题                                            | 不判断“符合”，只描述差距           |
| 撰写 Agent                        | 按模板逐条起草，句句带引用                                                | 无引用不写结论性句子               |
| 引用校核 Agent                    | 独立复核引用是否现行、适用范围是否匹配、型号/数字是否一致                 | 发现不一致即阻断，不“润色”过去     |
| 汇总 Agent（Supervisor 收口）     | 生成应答包、偏离表草稿、风险摘要、待确认清单                              | 不生成“可提交”结论                 |

**人在哪一步审批**

1. 技术负责人逐条确认“适用性”和“技术结论”，对不确定项签字标注。
2. 商务确认报价、交付期、服务承诺；法务审合同与法律条款。
3. 授权签字人签字、盖章、提交。**Agent 不接触签字与提交权限。**

**输出物**

- 条款级应答初稿（逐条带引用）
- 技术偏离表草稿
- 证据索引（证书/报告编号、有效期、对应条款）
- 缺口与风险清单
- 引用溯源表 + 完整审批记录

**验收指标（POC 目标，须以基线校准）**

| 类型   | 指标                     | 口径                                                            |
| ------ | ------------------------ | --------------------------------------------------------------- |
| 硬门槛 | 引用可追溯率 100%        | 每条结论可回链到标准号+条款号+版本+证据文件；无来源必须显式标注 |
| 硬门槛 | 抽检错引数 0             | 验收抽样 20–30 条，人工复核版本/适用范围/型号                   |
| 硬门槛 | 未经审批提交 0           | 审计日志核对                                                    |
| 业务   | 条款覆盖率 ≥95%          | 以人工清单为基准                                                |
| 业务   | 初稿人工一次采纳率 ≥60%  | 不改动或仅小改即可进入下一环节                                  |
| 业务   | 单包编制工时下降 20%–35% | 同口径基线对比                                                  |
| 业务   | 漏项数 0                 | 抽样核对                                                        |

**4–8 周节奏建议**

| 周    | 动作                                                           | 产出/决策点                       |
| ----- | -------------------------------------------------------------- | --------------------------------- |
| W1    | 访谈 + 基线测量；取 2 份历史认证包、1 份历史标书；确认数据权限 | 基线表、样本集、Q1/Q2/Q4 初步答案 |
| W2    | 定义条款 schema 与引用四要素；建最小映射表；建 50–100 条评测集 | 底座 v0、评测集                   |
| W3    | 搭 6 个角色 Agent 与流水线；接引用回链                         | 可回放的 demo                     |
| W4    | 离线回放历史样本，人工评审，修 Skill/提示词                    | 问题清单、v1                      |
| W5–W6 | 在 1 个真实项目影子运行（AI 出稿，人照常出稿，双轨对比）       | 双轨工时与差异报告                |
| W7    | 抽样验收 + 审计检查                                            | 验收报告                          |
| W8    | 复盘；决定是否扩到投标侧、更多机型                             | Go/No-Go                          |

> 4 周可交付“单场景 demo + 离线评测”；8 周才具备“影子运行 + 抽样验收”。不建议压缩到 4 周就承诺生产效果。

### 4.2 POC-2：供应链准入的证据包（次选）

**场景**

新供应商准入、年度复审、品类扩展时，把证书、认证范围、检测报告、社会责任承诺、品类标准规则逐条比对，形成可会签的证据包。上游判定明确：**只到“证据包 + 风险提示”，不碰准入结论。**

**输入**

- 供应商证书扫描件、认证范围、有效期
- 检测报告、体系证书、社会责任承诺书
- 品类标准规则、合同条款模板、绿色供应商评价要求
- 历史准入档案（抽样 5–10 份）、退回/返工记录

**多智能体分工**

| 角色           | 职责                                                         | 关键约束                         |
| -------------- | ------------------------------------------------------------ | -------------------------------- |
| 证书识别 Agent | OCR + 结构化：证书编号、发证机构、有效期、认证范围、标准依据 | 低置信字段标“待核”，不猜         |
| 条款比对 Agent | 按品类规则逐条比对，输出命中/未命中/待核                     | 不做“通过/不通过”结论            |
| 证据缺口 Agent | 列缺件、过期、范围不符、信息不一致                           | 过期与范围不符一律红灯           |
| 风险摘要 Agent | 生成红黄灯与复核建议                                         | 只描述事实与差距，不写“建议准入” |
| 汇总 Agent     | 出证据包与有效期日历                                         | 不写回任何准入字段               |

**人在哪一步审批**

1. 采购经办核对原件与扫描件一致性。
2. 质量/采购会签人做准入结论；过期、范围不符、无法识别三类强制人工复核。
3. 准入结果写回由人在原系统完成；首期 Agent 不写回。

**输出物**

- 证据包（逐项命中/未命中/待核）
- 红黄灯与复核建议
- 证书有效期日历
- 缺口清单与补件通知草稿（由人发送）

**验收指标**

| 类型   | 指标                        | 口径                       |
| ------ | --------------------------- | -------------------------- |
| 硬门槛 | 过期证书漏检数 0            | 规则确定性高，按硬指标验收 |
| 硬门槛 | 证据可追溯率 100%           | 每条比对可回到证书页/条款  |
| 硬门槛 | Agent 写回准入结论 0        | 审计日志核对               |
| 业务   | 证书关键字段抽检准确率 ≥98% | 抽 30–50 个字段人工核对    |
| 业务   | 单家评审工时下降 30%–45%    | 同口径基线对比             |
| 业务   | 会签一次通过率提升          | 退回原因分类对比           |

**6 周节奏建议**

| 周    | 动作                                               | 产出/决策点         |
| ----- | -------------------------------------------------- | ------------------- |
| W1    | 取 5–10 份历史档案；盘点品类规则与证书类型；测基线 | 基线、样本、Q5 答案 |
| W2    | 规则结构化；建字段与评测集                         | 规则表、评测集      |
| W3–W4 | 搭识别/比对/缺口/摘要 Agent；历史回放              | 证据包 v1           |
| W5    | 影子运行 10–20 家（AI 出包，人照常审）             | 差异与工时报告      |
| W6    | 抽样验收；确认是否扩品类                           | Go/No-Go            |

### 4.3 POC-3：运维作业的标准注入（第二期/备选）

**场景**

标准换版或新增后，反查受影响的手册章节、巡检判据、课程、合同条款，产出修订建议稿。上游判定：作业链是“弱约束”环节，最易失真，但集成最重，故放第二期。

**输入**

- 标准变更单、新旧版本条款 diff
- 手册章节、巡检规则、课程大纲、合同模板
- 机型/场站/系统映射
- 专业工程师与作业主管名单

**多智能体分工**

| 角色               | 职责                              | 关键约束                   |
| ------------------ | --------------------------------- | -------------------------- |
| 变更解析 Agent     | 读 diff，提取实质变更点           | 区分编辑性修改与实质性修改 |
| 影响载体识别 Agent | 按引用关系反查手册/巡检/课程/合同 | 输出候选清单，不直接改原文 |
| 改稿建议 Agent     | 生成 diff 式修订建议              | 保留原文结构，不重写整篇   |
| 一致性校核 Agent   | 查漏改、错改、术语不一致          | 独立复核，不与改稿同角色   |
| 汇总 Agent         | 出影响面报告与待确认清单          | 不发布、不写回             |

**人在哪一步审批**

1. 专业工程师签认技术内容与修订建议。
2. 作业主管/培训主管签认发布范围。
3. 发布仍走原手册系统、培训平台、巡检规则系统流程；Agent 只交建议稿。

**输出物**

- 影响面清单（按载体、机型、场站）
- 修订建议稿（diff）
- 一致性校核报告
- 待确认问题清单

**验收指标**

- 影响载体召回率 ≥90%（对照人工清单）
- 建议稿采纳率 ≥50%
- 换版排查周期下降 30%–50%
- 抽检错改/漏改数 0
- 未经签认的发布 0

**8 周节奏建议（须先满足前置条件）**

| 周    | 动作                                 | 产出/决策点    |
| ----- | ------------------------------------ | -------------- |
| W1    | 确认 Q3/Q6/Q7；取 1 次真实换版做样本 | 样本、接口清单 |
| W2    | 建“标准—载体”引用表                  | 映射表 v0      |
| W3–W4 | 搭变更解析/影响识别/改稿/校核 Agent  | 建议稿 demo    |
| W5–W6 | 在 1 次换版上影子运行                | 影响面对比     |
| W7    | 抽样验收                             | 验收报告       |
| W8    | 决定是否接入手册/培训系统            | Go/No-Go       |

> 前置条件不满足（无引用表、系统无接口、责任人不明确）时不启动 POC-3，避免把“文档库”包装成“作业自动化”。

### 4.4 三个 POC 的关系

```
POC-1 认证/投标应答  ──┐
                       ├── 共用：条款级检索 + 版本台账 + 映射表（P2/P1 底座）
POC-2 供应链准入证据包 ─┤
                       │
POC-3 作业标准注入    ──┘（第二期，依赖“标准—载体”引用表）
```

- **先做 POC-1**：多角色分工最自然、人工签批点最清晰、逐条可抽样，失败成本可控。
- **再做 POC-2**：规则最明确，但判定风险高，必须先把“不自动准入”写死。
- **POC-3 放第二期**：业务价值最高，但涉及三处系统集成，先用 POC-1/2 把底座和责任边界跑顺。
- **P2/P1 不单独立项**：作为共用底座随 POC-1 交付；单独做容易被当成“又一个文档库”。

**协作模式选择口径**：Supervisor 负责“动态分派 + 异常收口”，适合任务边界不完全固定、需要跨角色汇总的场景（如 POC-1 的解析与汇总）；Pipeline 负责“固定顺序 + 逐步可回放”，适合规则明确、责任链必须清晰的场景（如 POC-2 的证书识别→比对→缺口→摘要）。高风险链路优先 Pipeline，避免多角色自由对话导致责任漂移；Supervisor 不替人做结论，只做调度与汇总。

## 五、怎么工作：造、跑、治理、观测是能力与工作方式

> 以下四项是**内部能力语言**，解释“怎么做到”，不作为对外一句话主标题，也不替代主叙事。对外仍只说一句：面向企业的多智能体协作，在运行时上把业务自动做起来。

### 5.1 造：把业务配成岗位

“造”不是写一个万能助手，而是把业务拆成岗位卡，再配置成 Agent：

| 配置项 | 内容                                  | 金风示例                                                     |
| ------ | ------------------------------------- | ------------------------------------------------------------ |
| 角色   | 岗位名、职责边界、上下游              | 认证应答工程师、供应商准入评审助理、作业文件同步工程师       |
| 能力   | 可调用的 Skill/工具、知识域、输出契约 | 条款检索、证书解析、偏离表生成、引用校核、影响面反查         |
| 触发器 | 事件、定时、会话                      | 新招标/新证书/标准换版触发；每月标准更新监测；工程师主动提问 |
| 会话   | 任务上下文、交接、人工插入、暂停恢复  | 一个认证包一个会话；中途可转人工；审批后继续                 |

**角色卡必须写清“禁止动作”**：不签字、不盖章、不写回准入结论、不发布作业文件、不对外提交。禁止动作不是提示词，而是权限与流程约束。

### 5.2 跑：运行时 + MCP/Skill，让 Agent 真办事

- **运行时**负责编排：Supervisor 分派、Pipeline 顺序执行、失败重试、人工中断与恢复、长任务状态保存。
- **MCP/Skill** 负责“长出手脚”：接标准库、文档系统、证书 OCR、招采/供应商系统、手册/培训系统。**具体有哪些连接器、能否写回，需实施评估，本文不预设。**
- **模型路由**：按任务选择模型；敏感材料走私有化模型或客户批准的通道，不出域。
- **工具调用留痕**：每次检索、比对、生成、写回尝试都记录参数与结果，便于回放。
- **沙箱**：文件解析、OCR、格式转换在隔离环境执行；不把客户文档带到未授权环境。

### 5.3 治理：权限事先定好，审批和审计是流程的一部分

| 治理项     | 做法                                                                             | 落点                |
| ---------- | -------------------------------------------------------------------------------- | ------------------- |
| RBAC       | 角色：标准化管理员、认证工程师、采购、质量、法务、作业主管、只读审计；按岗位授权 | 每个 POC 的审批矩阵 |
| 文档级权限 | 按项目/机型/市场/密级隔离；供应商材料按项目隔离                                  | 知识底座与检索层    |
| 审批/HITL  | 审批节点配置在流程里，不可由 Agent 跳过；超时升级；审批人不能是发起 Agent        | 提交、写回、发布前  |
| 审计       | 记录输入、检索命中、引用、工具调用、审批人、时间、模型版本；支持回放与导出       | 每次会话            |
| 审计验真   | 哈希链校验，防篡改（企业版能力）                                                 | 对外/监管场景       |
| 熔断       | Kill switch；错误率、敏感操作、越权尝试触发停止                                  | 运行时              |
| 多租户     | 集团/子公司隔离；跨主体写入需企业版能力                                          | 部署形态            |

**Open-Core 口径**：社区版可自托管，适合单主体 POC；企业版通过许可证解锁多租户写、他人 HITL 决策、审计验真等能力（以实际版本为准）。若金风以集团多主体方式推广，需在 POC 后评估企业版；POC 阶段可先用单租户隔离验证业务价值。

### 5.4 观测：做完能查到每一步

- **会话回放**：从收到任务到产出初稿，每一步检索、引用、工具调用、人工修改都可查。
- **指标看板**：任务量、条款覆盖率、引用回链率、拒答率、人工采纳率、审批时长、异常升级数。
- **评测集**：固定 50–100 条“问题—正确条款—正确版本”样本，每次改 Skill/提示词都回归。
- **审计导出**：按项目导出“引用溯源表 + 审批记录”，作为认证/投标/内审的佐证材料。
- **告警**：引用回链失败、审批超时、越权尝试、模型异常，进入运维告警队列。

### 5.5 部署形态：自托管，数据不出域

- **部署**：客户内网/私有云，容器化；POC 与生产环境隔离；支持备份、升级窗口、最小权限账号。
- **数据**：标准文本、向量索引、会话记录、审计日志均落在客户侧；敏感材料不出域。
- **模型**：优先客户私有化模型或客户批准的模型通道；跨域调用需单独评估。
- **集成**：只读优先；写回单独立项，需草稿态、审批、回滚、审计四件套。
- **规模**：POC 建议 1 个业务域、1–2 个机型/品类、20–50 名用户；不追求全集团铺开。
- **待评估**：具体拓扑、资源规格、SLA、灾备等级、标准文本采买方式，需实施评估后出。

## 六、效益假设：只做容量级测算，不是 ROI 承诺

> **重要声明**
>
> - 以下数字是**假设测算**，用于判断“是否值得做 POC”，**不是已验证 ROI、不是收益承诺、不是报价依据**。
> - 参数来源分三类：客户公开数据（仅用于规模感）、行业公开案例的定性结论、FDE 经验值。**均未经金风基线验证**，POC 第 1 周必须用客户真实基线替换。
> - 测算不含软件许可、算力、集成、标准采买、客户人力投入；也不把“节省人日”等同于“裁员”。

### 6.1 测算表

| 切口                 | 测算公式                               | 假设参数（来源）                                                                                                                                                                     | 保守              | 中性               | 上限               |
| -------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------- | ------------------ | ------------------ |
| POC-1 认证/投标应答  | 年应答包数 × 单包人日 × 可压缩比例     | 年 80–120 包（假设：H1 92 张证书中约 1/3–1/2 需完整应答，加投标样本；**客户公开数据 F17 + 经验值**）；单包 4–6 人日（**FDE 经验值**）；压缩 15%–35%（**行业案例定性结论 + 经验值**） | 约 50 人日/年     | 约 125 人日/年     | 约 250 人日/年     |
| POC-2 供应链准入     | 年评审家数 × 单家人日 × 可压缩比例     | 年 100–150 家（**经验值，待 Q5**）；单家 0.8–1.2 人日（**经验值**）；压缩 30%–45%（规则明确、结构化程度高，**经验值**）                                                              | 约 25 人日/年     | 约 45 人日/年      | 约 80 人日/年      |
| POC-3 作业标准注入   | 年换版次数 × 单次排查人日 × 可压缩比例 | 年 20–40 次（**经验值，待 Q3/Q6**）；单次 4–6 人日（**经验值**）；压缩 20%–35%（**经验值**）                                                                                         | 约 15 人日/年     | 约 40 人日/年      | 约 85 人日/年      |
| **合计（POC-1+2）**  | —                                      | —                                                                                                                                                                                    | **约 75 人日/年** | **约 170 人日/年** | **约 330 人日/年** |
| **合计（含 POC-3）** | —                                      | —                                                                                                                                                                                    | **约 90 人日/年** | **约 210 人日/年** | **约 415 人日/年** |

按 220 人日/FTE 折算，中性约 **0.8–1.0 FTE**。这个量级不足以支撑“大幅降本”的叙事，**真正的价值在周期、错引率、可追溯性和专家依赖**，不在人头数。

### 6.2 不货币化的价值（更应作为验收重点）

- **周期**：认证/投标从“收文到初稿”的时间缩短；换版影响面排查从“各部门自查”变成“一张清单”。
- **质量**：错引过期条款、漏项、证书过期漏检减少；每条结论可回链。
- **可追溯**：认证/投标/内审可导出引用与审批记录，减少“谁说的、依据哪版”的扯皮。
- **知识资产**：条款索引、映射表、评测集沉淀为可复用底座，后续扩场景边际成本下降。
- **风险**：把“人找文件”变成“系统给依据 + 人签字”，责任边界更清楚。

### 6.3 投入侧假设（同样需评估）

- POC 周期 6–8 周；FDE 2–3 人（方案/工程/评测），客户侧 1 名业务 owner + 1 名 IT 接口人 + 若干评审专家。
- 不含标准文本采买、系统改造、历史数据清洗的额外工作量；这些需在 W1 评估。
- 如果客户已有标准管理系统，工作量下降；如果没有，映射表建设是主要成本。

## 七、不做 / 暂不做清单

| 不做/暂不做                                     | 原因                                      | 替代做法                               |
| ----------------------------------------------- | ----------------------------------------- | -------------------------------------- |
| 认证/检测最终签字、盖章                         | 授权签字人不可代理；原始记录不可修改      | Agent 只出初稿与证据包，人签字         |
| 供应商准入“通过/不通过”                         | 过期、范围不符不得自动准入；责任在会签人  | 出证据包 + 红黄灯，人做结论            |
| 设计红线“符合/不符合”判定                       | LLM 不能直接判定符合性；须专业工程师签认  | 找条款、列证据、标不确定               |
| 安全类定级、作业许可（停电/动火/高空/受限空间） | 安全措施必须人审、硬联锁、权限隔离        | 提供标准依据与检查项，不签发           |
| 对外披露、ESG/可持续报告口径                    | 对外数字须人工核对来源与证据级别          | 不生成对外定稿                         |
| 报价、交付承诺、合同法律条款终稿                | 商务与法律后果不可由 Agent 承担           | 出草稿与风险提示，人定稿               |
| 直接写回 QMS/CMMS/ERP/招采平台                  | 无草稿态、审批、回滚、审计不可上线        | 首期只出草稿；写回单独立项             |
| 培训问答包装成“业务自动化”                      | 单点 RAG 足够，多智能体增加成本与不确定性 | 单 Agent 试水，不做 POC                |
| P6 专家复用上多智能体                           | 价值难量化、数据缺口大                    | 单点 RAG + 专家评审                    |
| 全量标准自动入库                                | 版权、密级、授权未确认                    | 按来源分层授权，先小范围               |
| 跨主体/跨项目数据共享                           | 数据权限与合规风险                        | 项目隔离；多租户需企业版评估           |
| 自动生成“可提交/可签署”结论                     | 越权签发风险                              | 输出只标“通过/不通过/待核”，不写“可签” |

## 八、风险与缓解

| 风险                    | 具体表现                                               | 缓解措施                                                                                                       | 责任              |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- | ----------------- |
| **标准版本错配**        | 引用了被替代版本、未生效版本；同一问题不同版本答案混用 | 引用强制四要素；版本台账 + 替代关系；检索按“任务日期/机型/市场”过滤；校核 Agent 独立复核；上线前标准化归口确认 | 标准化归口 + 产品 |
| **引用不可追溯**        | 答案看起来对，但找不到条款/证据；无法应对审计          | 无来源不回答；句句带引用；引用回链率 100% 作为硬门槛；会话留存检索快照与语料版本                               | 产品 + 审计       |
| **越权签发**            | Agent 生成“可签/可提交”结论；或绕过审批写回系统        | 权限与流程约束，不靠提示词；Agent 无签字/提交/写回凭证；四眼原则；越权测试纳入验收；熔断                       | 治理 + 客户责任人 |
| **数据权限**            | 供应商材料、标书、企标跨项目泄露；集团/子公司越权      | 文档级 ACL；项目隔离；最小权限；脱敏；多租户写需企业版；定期权限复核                                           | IT + 安全         |
| **模型幻觉**            | 编造条款号、标准名、证书有效期；把“相似”当“匹配”       | RAG 限定语料；结构化抽取；低置信标“待核”；拒答机制；评测集回归；人工抽样                                       | 产品 + 业务专家   |
| **证书 OCR/结构化错误** | 有效期、认证范围识别错，导致误判                       | 关键字段双通道校验；低置信人工复核；过期/范围不符强制红灯；抽检准确率门槛                                      | 采购 + 质量       |
| **标准版权/授权**       | IEC/企标超范围使用；对外传播                           | 来源分层授权；入库前版权确认；访问控制；不整篇外传                                                             | 法务 + 标准化     |
| **系统集成失败**        | 手册/培训/招采系统无 API 或权限不足                    | W1 做接口盘点；只读优先；写回单独立项；不承诺未验证的连接器                                                    | IT + FDE          |
| **组织采纳不足**        | 业务仍按老流程；Agent 产出无人用                       | 选真实项目影子运行；业务 owner 深度参与；验收看采纳率不看 demo；培训与激励                                     | 客户业务 owner    |
| **责任边界模糊**        | 出问题后“是 AI 说的”                                   | 审批矩阵写清唯一责任人；审计记录到人；对外文件只认签字人                                                       | 双方项目组        |

## 十、一页结论

1. **主叙事**：面向企业的多智能体协作，在运行时上把业务自动做起来。金风的落点是让标准知识在认证、投标、供应链准入、作业现场被岗位型 Agent 调用，而不是再建一个文档库。
2. **三个 POC**：① 认证/投标符合性应答（首选，8 周）② 供应链准入证据包（次选，6 周）③ 运维作业标准注入（第二期，8 周）；P2/P1 只做共用底座，不单独立项。
3. **人在哪里签字**：技术、商务、法务三签；采购+质量会签；授权签字人签字提交；作业/培训主管签认发布。Agent 不签字、不盖章、不写回结论。
4. **怎么工作**：造（岗位卡/能力/触发器/会话）→ 跑（运行时 + MCP/Skill）→ 治理（RBAC、HITL、审计、熔断）→ 观测（会话回放、指标、评测集、审计导出）；四项是能力展开，不是对外主标题。
5. **效益**：中性约 0.8–1.0 FTE 的容量级假设，真正价值在周期、错引率、可追溯与专家依赖；所有数字均标假设，不是 ROI 承诺。
6. **边界**：认证签字、准入结论、设计红线、安全许可、对外披露、报价/法律终稿、系统直接写回，均不做；培训问答不包装成业务自动化。
7. **未签约**：金风科技不是 Agent Forge 客户，本文不构成合作、交付或效果承诺；对外使用前须人工核对公开信息与证据级别。
