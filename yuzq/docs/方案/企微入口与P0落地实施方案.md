## 1. 能力边界与分期

### 1.1 能力切分（事实）

| 代号 | 内容 | 不包含 |
| --- | --- | --- |
| 企微入口 | 企业微信内收发消息与文件，创建/驱动 Agent Forge 上的协作任务 | 不替代销售易登录；不等于 P0-A/P0-B 业务算法本身 |
| P0-A | 会审开始前的合同智能录入（抽取、物料候选、缺件、预填草稿、人工确认） | 不含会审结论；不含业务风险「签了会怎样」 |
| 会审 | 客户既有人工审批链 | 不是 P0-B |
| 评审辅助（可选） | 既有「合同评审」协作产出的分层评审卡，供会审人参考 | 不等于 P0-B 的业务风险卡 |
| P0-B | 会审意见产生之后的业务视角风险评估报告 | 不定责、不输出「建议签署/不建议签署」 |
| 销售易接通 | S4：草稿等字段写回或拉单 | S0–S3 可不实施 |

数据流（白话）：

```text
员工在企业微信里发合同
  → 「企微对接服务」（下文称 Bridge）收下消息、认出是谁、把文件交给 Agent Forge
  → Agent Forge 跑录入/风险等任务，并把进度告诉对接服务
  → 对接服务再回消息到企业微信
  →（后期 S4）确认后的草稿写入销售易
```

### 1.2 分期

| 阶段 | 交互侧可验证现象 | 实现侧交付物 |
| --- | --- | --- |
| S0 | 应用可见范围内成员可传文件并收到受理与阶段消息 | 自建应用 + 企微对接服务 + 通讯录同步建身份 + 进度推送 + 控制台确认链接 |
| S1 | 同一入口可跑完录入并确认出草稿 | 对接服务触发录入协作；人工确认在控制台完成 |
| S2 | （可选）可打开评审卡 | 触发既有评审协作 |
| S3 | 提交会审意见后可收到风险摘要 | 新建会审后风险评估协作 |
| S4 | 确认后的草稿出现在销售易 | SSO/绑定 + 写回 API |

## 2. 入口形态

### 2.1 交互

- 用户从企业微信**工作台**打开名为「合同助手」的应用，进入与该应用的会话。  
- 在该会话中发送文本与文件（PDF / Word / 常见图片）。  
- 主路径不要求用户先加入群并 @群机器人。  
- 销售易页面内按钮跳转 H5 不作为 S0 前提。

### 2.2 实现

| 选项 | 结论 | 事实依据 |
| --- | --- | --- |
| 企业微信**自建应用** | S0 采用 | 支持应用会话收消息、收文件、配置回调 URL、按可见范围授权成员 |
| **群机器人**（Webhook） | 不作主入口 | 以群内出站通知为主；入站文件与稳定成员会话能力弱于自建应用 |
| 销售易内嵌按钮 | S4 | 依赖销售易侧扩展与登录态打通 |

对外口头可称「企微助手/机器人」。真正要交付的是：**企业微信自建应用 + 企微对接服务（Bridge）**，不是群里那种只能发通知的 Webhook 机器人。

配置项（企业微信管理端）：应用 AgentId、Secret、回调地址与加解密参数、可信 IP/域名、应用可见范围（谁能用）。

### 2.3 Bridge 是什么（先读清楚）

**Bridge = 我们自己要写/部署的一个「企微对接服务」。**  
它不是企业微信自带功能，也不是 Agent Forge 内核里的某个开关。它是夹在中间的一个独立小服务。

三边关系：

```text
企业微信  ←→  Bridge（企微对接服务）  ←→  Agent Forge
```

| 它做什么 | 白话 |
| --- | --- |
| 接企微消息 | 员工在应用里发文件/文字，企微推到我们服务器；Bridge 负责验真、解密、看懂「谁发的、发了什么」 |
| 认人 | 根据企微成员 ID，按固定规则对应到 Agent Forge 里的任务归属人（见第 3 章）；需要时同步通讯录 |
| 调 Agent Forge | 用机器账号调用 Agent Forge：建任务、挂附件、查进度 |
| 回消息给企微 | 把「已受理」「做到哪一步」「去确认」发回员工的企微会话 |
| 给确认链接 | 需要人工点确认时，生成短时有效的控制台链接（打开就是这个人的这个任务） |

| 它不是什么 | |
| --- | --- |
| 不是群机器人 Webhook | 群机器人主要是往群里推一句通知，接不住完整「一人一会话 + 收文件」主路径 |
| 不是 Agent Forge 本体 | 合同怎么抽、怎么评，仍在 Agent Forge 里跑；Bridge 只负责企微进出 |
| 不是给用户看的产品名 | 用户只看到「合同助手」应用；Bridge 是实施侧组件名 |

一句话：**用户只跟企微应用聊天；Bridge 在后台把聊天翻译成 Agent Forge 的任务，再把结果翻译回企微消息。**

## 3. 身份与账号映射

### 3.0 一句话说明（先读这段）

**要做通讯录同步。映射不是手填「张三 → alice」。**

企微里每个人本来就有一个成员 ID（`userid`）。**企微对接服务（Bridge）**把通讯录里的人拉过来（或人一发消息就按规则建一条），用固定公式生成 Agent Forge 里的任务归属人 ID（`owner_id`）：

```
企微 userid = zhangsan
corp_id     = wwxxxx
        ↓ 固定规则（代码写死）
AF owner_id = wecom:wwxxxx:zhangsan
```

所以：

| 问题 | 答案 |
| --- | --- |
| 映射怎么来的？ | **公式算出来的**，不是 Excel 对照表手填 |
| 要不要通讯录同步？ | **要**（生产主路径）。用来知道有哪些人、谁离职了 |
| 人要做什么？ | 企微里划「谁能用这个应用」；实施侧只配一次「这家企微企业 = 哪个 AF 租户」 |
| 不用做什么？ | 不用给每个员工单独开 AF 账号、不用维护每人一行映射 |

没有通讯录权限时（S0 临时）：从应用可见范围导出成员名单，**仍用同一公式批量生成**，不是换一套手填映射。

### 3.1 交互

- 应用可见范围内的在职成员发消息即可用，无「先找人开通 Agent Forge 账号」的日常步骤。  
- 「去确认」经短时 ticket 进入控制台对应会话（S0/S1）；不向终端用户暴露桥接服务账号密码。  
- 用户 A 的任务 `owner_id` 为 A；与用户 B 隔离。  
- 不在可见范围、已离职、或被禁用的成员：固定拒绝文案，不建会话。

### 3.2 实现

#### 3.2.1 两侧标识

| 系统 | 标识 | 作用 |
| --- | --- | --- |
| 企业微信 | `corp_id` + `userid` | 企业与成员；回调与发消息寻址 |
| Agent Forge | `tenant_id` + `owner_id` + `role` | 租户隔离、会话归属、RBAC、HITL、审计 |

#### 3.2.1a 鉴权：谁可以调？（不是谁都行）

**不是谁都可以调。** 分三道门，业务员工也不直接调 Agent Forge。

| 谁 | 能不能调 | 怎么拦 |
| --- | --- | --- |
| 随便一个外网调用者 | **不能**调 Bridge 回调、**不能**调 Agent Forge | Bridge 校验企微签名；Agent Forge 要账号密码（Basic Auth） |
| 未划进应用可见范围的员工 | **不能**用合同助手 | 企微侧根本进不了应用 / 发了也被 Bridge 拒绝 |
| 可见范围内的员工 | **只能**在企微里发消息，**不能**拿密码去调 API | 员工没有 Bridge/AF 的机器账号 |
| Bridge（对接服务） | **可以**调 Agent Forge | 持有唯一机器账号 + 密码；密码只放在服务器配置里 |
| 控制台「去确认」链接 | **只能**打开链接里那个人、那个任务 | 短时 ticket，过期作废；不能拿来当通用密码 |

白话流程：

```text
1. 员工在企微发文件
   → 企微服务器推给 Bridge（带签名）
   → Bridge 验签失败 = 丢掉（假冒推送进不来）

2. Bridge 认出 userid
   → 不在可见范围 / 已禁用 = 回复拒绝，不建任务
   → 通过才继续

3. Bridge 用「机器账号+密码」调 Agent Forge
   → 没密码 = Agent Forge 直接 401
   → 有密码后：任务挂在该员工对应的 owner_id 名下（映射只决定「任务算谁的」，不代替登录）

4. 员工点「去确认」
   → 打开带 ticket 的控制台链接
   → 只能进这一单；不是拿到了全站权限
```

要分清两件事：

| | 作用 |
| --- | --- |
| **鉴权（能不能调）** | 企微验签 + Bridge 机器账号调 AF + ticket 打开控制台 |
| **映射（任务算谁的）** | `userid` → `owner_id`，只决定会话归属与隔离，**不是**每人一套登录密码 |

约束：机器账号密码不发给业务用户；禁止全员共用同一个业务 `owner_id`（否则任务分不清是谁的）。

#### 3.2.2 自动建档（主路径）

| 步骤 | 事实 |
| --- | --- |
| 1. 通讯录同步 | Bridge 调企业微信通讯录 API（或收通讯录变更回调）：拉取/增量成员与部门 |
| 2. 确定性 `owner_id` | 对每个在职且落入应用可见范围的 `userid`，计算 `af_owner_id = wecom:{corp_id}:{userid}`（规则写死，不靠人手填） |
| 3. 写入/更新链接表 | upsert `wecom_identity_link`：`af_tenant_id` 取该 `corp_id` 绑定的租户；默认 `af_role` 取租户默认角色（如 `operator`） |
| 4. 离职/移出可见范围 | 同步任务将 `status=disabled` 或删链接；此后回调拒绝 |
| 5. 首次发消息兜底 | 若回调命中时尚无行：即时按同一规则 upsert 一行（仍非人工录入），再继续建会话 |

`wecom_identity_link` 是**同步结果的物化表**，不是主数据录入表。

| 字段 | 来源 |
| --- | --- |
| `corp_id` / `userid` | 企微通讯录 |
| `af_tenant_id` | 配置：一个 `corp_id` 绑定一个 AF 租户 |
| `af_owner_id` | 规则生成，见上 |
| `af_role` | 默认角色；仅例外名单可覆盖 |
| `status` | 同步状态（在职可见 = active） |
| `display_name` 等 | 通讯录只读缓存（可选） |

请求路径：

1. 回调验签 → 解析 `corp_id`、`userid`。  
2. 读链接表；无行则走「首次发消息兜底」upsert；`disabled` 则拒绝。  
3. 桥接服务账号调 AF；session/run 的 `owner_id`/`tenant_id` 取链接行。  

约束：禁止全员共用同一 `owner_id`。

#### 3.2.3 人需要碰的配置（非每人一行）

| 配置项 | 说明 |
| --- | --- |
| `corp_id` ↔ `af_tenant_id` | 企业级绑定，一次 |
| 应用可见范围 | 在企微管理端划定谁能用应用（通讯录侧授权） |
| 默认 `af_role` | 租户默认 |
| 例外表（少量） | 指定 userid 升为 `approver`/`admin`，或强制 `disabled` |
| 对接服务机器账号 | Bridge 调 Agent Forge 时用的服务账号密码；不是业务员工的登录账号 |

S0 若通讯录 API 尚未开通：允许**临时**用可见范围成员列表导出后批量导入，仍按同一 `owner_id` 规则生成，不做「人工逐人想一个 AF 用户名」。该临时手段在通讯录同步上线后废弃。

#### 3.2.4 控制台深链与 S4

Bridge 签发短时 **ticket**（`tenant_id`、`owner_id`、`session_id`/`run_id`、过期时间）→ 控制台换会话。  
S4：`userid` → `af_owner_id` → 销售易用户主键；销售易侧绑定同样优先自动（工号/手机号对齐或 IdP subject），例外再人工。

### 3.3 操作流程（谁做什么）

分三类角色：**企微管理员**、**我方实施/运维**、**业务用户**。日常加人/减人走企微通讯录与应用可见范围，不走「在 AF 里开账号」。

#### 3.3.1 一次性上线（实施）

```
1. 企微管理端
   创建自建应用 → 配 AgentId/Secret、回调 URL/Token/EncodingAESKey
   → 划定「应用可见范围」（部门或人员 = 谁能用）
   → 开通通讯录只读（或成员变更回调）权限

2. 我方配置（租户级，非按人）
   写入 corp_id ↔ af_tenant_id
   → 设默认 af_role（如 operator）
   → 配 Bridge 服务账号（AF Basic Auth / IDENTITY_MAP 绑机器账号）
   → 配例外表（可选：少数 approver/admin，或强制 disabled）

3. 首次全量同步
   Bridge 拉通讯录（或按可见范围成员）
   → 对每个在职且可见的 userid
   → 自动 upsert wecom_identity_link
      af_owner_id = wecom:{corp_id}:{userid}
   → 验收：抽查若干人链接行存在且 status=active
```

#### 3.3.2 日常变更（自动，管理员只动企微）

| 业务动作（企微侧） | 系统动作 | 人是否还要在 AF 操作 |
| --- | --- | --- |
| 新员工入职且被划进应用可见范围 | 同步任务或变更回调 → 自动建链接行 | 否 |
| 员工离职 / 移出可见范围 | 同步 → `status=disabled`（或删链接） | 否 |
| 改姓名/部门 | 可选更新 `display_name` 等缓存字段 | 否 |
| 要把某人提成审批人 | 在**例外表**写一条 role 覆盖（少量） | 仅改例外，不改对照表主数据 |
| 某人误用/安全停用 | 例外表强制 `disabled`，或移出可见范围 | 二选一即可 |

同步触发方式（实现二选一或并用）：

- **定时全量/增量**：Bridge 定时调通讯录 API。  
- **事件驱动**：企微推送成员新增/更新/离职事件 → Bridge 即时 upsert。

#### 3.3.3 业务用户日常（无开通账号步骤）

```
用户已在应用可见范围
  → 工作台打开自建应用（或会话）
  → 发送合同文件
  → Bridge：验签 → 查 wecom_identity_link
       有行且 active → 用该 owner_id 建 AF 会话
       无行 → 按同一规则即时 upsert（兜底）再继续
       disabled / 不可见 → 回复拒绝文案，不建会话
  → 用户收到 L0 受理（含任务号）及后续阶段消息
  → 需确认时点「去确认」→ ticket 深链进控制台对应会话
```

业务侧**没有**「找 IT 开 Agent Forge 账号 / 填映射表」的日常流程。

#### 3.3.4 S0 临时兜底（通讯录 API 未开时）

```
1. 企微管理端导出应用可见范围成员（含 userid）
2. 实施侧跑一次性导入脚本：按同一规则批量 upsert 链接行
3. 上线后仍靠「首次发消息兜底」补漏
4. 通讯录同步开通后：关掉手工导出导入，改走 3.3.1/3.3.2
```

仍禁止：实施同学按人口头起一个自定义 AF 用户名再手填对照。

## 4. 消息与进度

### 4.1 交互

| 用户可见 | 内容约束 |
| --- | --- |
| 受理 | 含任务号；在收到文件后尽快返回 |
| 阶段进度 | 短句，对应业务阶段（提取 / 匹配 / 待确认等），条数少 |
| 待办 | 明确「去确认」及确认事项类型 |
| 结果 | 草稿完成说明，或风险摘要若干行 |
| 禁止默认推送 | 模型推理过程、工具调用名、原始 JSON、skill 内部名、置信度调试字段 |

### 4.2 实现

| 层级 | 是否推企业微信 | 产生方式 |
| --- | --- | --- |
| L0 受理 | 是 | Bridge 落盘附件并创建任务后同步回复 |
| L1 阶段 | 是 | 监听或轮询 Agent Forge 协作 run / 成员状态，映射为固定文案模板 |
| L2 摘要 | 是 | 从产物 Markdown 按模板截取 |
| L3 全文 | 否（仅 URL） | 控制台打开 session 产物 |
| L4 推理与工具轨迹 | 否 | 仅 Agent Forge 控制台或审计存储 |

HITL（物料候选、缺件、草稿确认）：S0/S1 主路径为控制台审批页；企业微信侧发送 L1 + ticket 链接。  
阶段超时：补发一条「仍在处理」类 L1；失败使用固定失败文案。

## 5. 组件关系

```text
企业微信自建应用
  → 回调至 WeCom Bridge
       · 验签
       · wecom_identity_link
       · 下载 media → 附件存储
       · L0/L1/L2 出站消息
       · 签发 ticket
  → Agent Forge API（桥接服务账号 Basic Auth）
       · tenant / owner 取自映射表
       · 启动录入 / 评审 / 会审后风险 等 team
  →（S4）销售易 API
```

WeCom Bridge 为独立进程；不把企业微信回调协议实现进 Agent Forge runtime 内核。

## 6. P0-A 会审前录入

### 6.1 交互

上传或声明「录合同」→ L0 → L1 → 确认页完成候选/缺件/草稿确认 → L2 通知草稿可用，按客户流程提交会审。S1 不声称已写入销售易。

### 6.2 实现

触发既有录入协作（pipeline）：收件识别 → 要素提取 → 清单匹配 → 缺件追问 → G1。  
任务元数据包含 `source=wecom` 与 `userid`。  
验收：字段有出处；无出处不写入正式值；清单匹配输出候选列表；G1 前草稿非生效态。

细节见 `poc/合同录入与初审演示方案.md`。

---

## 7. 会审与评审辅助

### 7.1 交互

会审节点与权限仍按客户组织执行。评审辅助卡供人阅读；会审意见由人产生。产品文案上区分「评审卡」与「会审后业务风险卡」。

### 7.2 实现

S2 可选：对已确认草稿启动既有合同评审协作，产出评审卡，G2 确认。  
P0-B 启动前置：合同文本或附件 + 会审意见文本（或结构化结论）。缺会审意见时：拒绝启动，或产出带「非正式」标记的草稿风险（默认拒绝更干净）。

---

## 8. P0-B 会审后风险评估

### 8.1 交互

用户提交会审意见（及合同引用）→ L0/L1 → L2 业务后果摘要（区分赊销/现款等场景标签）→ 可选打开全文与依据。输出不含签署建议句式。

### 8.2 实现

新建 team（建议名：会审后风险评估），pipeline 示例：

| 顺序 | 职责 | 产物文件名（示例） |
| --- | --- | --- |
| 1 | 校验会审意见与合同是否齐全，登记场景标签 | `风险收件.md` |
| 2 | 抽取回款/质保/调价/背靠背等相关条款及出处 | `风险条款要点.md` |
| 3 | 按场景写业务后果 | `业务后果.md` |
| 4 | 挂载法规/历史合同/内部规则条目；未命中写「无法判断」 | `风险依据.md` |
| 5 | 汇编并经 HITL 后落库 | `业务风险评估卡.md` |

与评审协作产物文件名、菜单入口分离。

## 9. S4 销售易

### 9.1 交互

人工确认后的草稿（及约定字段）可在销售易中查看；入口仍以企微为主时，不要求每个 CRM 页先加按钮才能演示 S0–S3。

### 9.2 实现

- 写回：仅允许的草稿字段；写前 HITL；失败可重试。  
- 身份：`userid` ↔ `af_owner_id` ↔ 销售易用户。  
- 登录：企业 IdP 或销售易侧 SSO，替换或增强 ticket。  
- 权限与审计按 Agent Forge RBAC + 客户 CRM 权限模型对齐（具体字段待接口勘察）。

## 13. 术语表

| 术语 | 含义 |
| --- | --- |
| **企业微信 / 企微** | 腾讯面向企业的即时通讯与办公平台；本文入口跑在此平台上的自建应用会话中 |
| **自建应用** | 企业微信管理后台创建的企业自有应用；可配置工作台入口、密钥、回调、成员可见范围 |
| **群机器人 / Webhook 机器人** | 群内出站通知机器人；本文不作为主对话入口 |
| **corp_id** | 企业微信**企业**的唯一 ID（企业维度）。同一家公司一个；用于区分我方演示企业与客户生产企业 |
| **userid** | 企业微信**成员**在该企业内的用户 ID。回调里标识「谁发的消息」；发消息也按此寻址 |
| **AgentId / Secret** | 自建应用的应用 ID 与密钥，调用企业微信 API 时使用 |
| **回调 URL / Token / EncodingAESKey** | 企业微信向我方服务器推送消息时的地址与验签/加解密参数 |
| **media_id** | 企业微信临时素材 ID；需调用企业微信接口下载文件二进制 |
| **WeCom Bridge / Bridge / 企微对接服务** | 我们自建的中间服务（独立进程）。夹在企业微信和 Agent Forge 之间：收消息、认人、建任务、回进度。用户看不见这个名字 |
| **通讯录同步** | 调用企业微信通讯录接口或接收成员变更事件，自动维护成员与 `wecom_identity_link`，无需按人手工建 AF 账号 |
| **wecom_identity_link** | 同步结果物化表：`userid` 与 `af_owner_id` 等的对应关系；主路径自动 upsert |
| **Agent Forge** | 多智能体协作运行时与控制台；会话、team、HITL、审计落在此系统 |
| **tenant_id / 租户** | Agent Forge 多租户隔离键。不同客户或演示环境使用不同租户，数据与权限隔离 |
| **owner_id / 所有者** | Agent Forge 中「任务属于谁」的用户键。影响会话列表、沙箱路径、HITL 归属 |
| **role / RBAC** | 角色与权限（如 admin、operator、approver、readonly）；约束谁能批 HITL、谁能写 |
| **Basic Auth** | Agent Forge HTTP 基本认证（用户名 + `AGENTFORGE_SERVER_PASSWORD` 或组织账号密码） |
| **AGENTFORGE_IDENTITY_MAP** | 环境变量：把 Basic 用户名绑定到固定 tenant/owner/role 的 JSON 配置 |
| **session** | Agent Forge 一次对话/任务会话 |
| **team / 协作 / run** | 多岗位流水线或主管制协作及其一次运行实例 |
| **pipeline** | 协作编排模式之一：岗位按固定顺序串行执行 |
| **HITL** | Human In The Loop，人工确认闸门（如确认草稿、确认卡片） |
| **ticket** | WeCom Bridge 签发的短时签名令牌，用于打开控制台时证明「已是映射用户且绑定某 session」 |
| **SSO** | Single Sign-On，单点登录；S4 与销售易/IdP 打通时使用 |
| **IdP** | Identity Provider，身份提供方（如企业统一认证） |
| **L0 / L1 / L2 / L3 / L4** | 本文定义的消息层级：受理 / 阶段进度 / 摘要 / 全文链接 / 推理轨迹（不推企微） |
| **P0-A / P0-B** | 优先级 0 的两块能力：会审前录入；会审后业务风险 |
| **会审** | 客户合同审批链上的人工评审过程 |
| **销售易** | 客户 CRM；合同模块等业务单据所在系统 |
| **G1 / G2** | 既有 poc 方案中的人工闸门编号（录入确认 / 评审卡确认） |
