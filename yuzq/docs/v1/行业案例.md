# 行业案例：企业级多智能体协作与业务自动化

> 用途：为防水材料制造商（B2B 工程渠道 + 经销渠道并重、销售人数多、合同量大）的方案设计提供外部对标。
> 范围：只收录公开可核验的**业界第三方案例**，聚焦两类形状——(1) 多智能体协作落地业务流程；(2) 文档/合同类业务自动化与销售赋能。
> **重要声明：本文所有案例均为业界公开案例，与 Agent Forge 无客户关系、无合作关系、未在本方环境复现。不得在任何对外材料中改写为「Agent Forge 客户案例」。**
> 检索时间：2026-10-22。

## 0. 证据级别口径

| 级别  | 定义                                                                                     | 本次使用说明                         |
| ----- | ---------------------------------------------------------------------------------------- | ------------------------------------ |

## 1. 结论速览

| #   | 主体                                 | 场景                                                | 与「面向企业 · 多智能体协作 · 业务自动化」的关系       | 证据级别 |
| --- | ------------------------------------ | --------------------------------------------------- | ------------------------------------------------------ | -------- |
| 1   | Harvey（法律 AI 平台）               | 合同 playbook 审查：主办 agent + 并行 worker agents | **强对齐**：真多智能体分工 + 冲突升级 + 人终审         | C        |
| 2   | Holcim（建材，瑞士）                 | 发票/单据 AI 分类与路由（Omnivore）                 | **部分对齐**：文档自动化闭环，但**非多智能体**         | B        |
| 3   | Schneider Electric（电气制造，法国） | 全球销售团队 Copilot for Sales + CRM 回写           | **部分对齐**：销售赋能嵌入工作流，但单点 copilot       | B        |
| 4   | KPN（电信，荷兰）                    | 销售赋能、RFP 摘要、报价草案                        | **弱对齐**：可量化的效率提升，但不构成业务闭环         | B        |
| 5   | Salesforce（自用，Customer Zero）    | SDR agent 跑线索、服务 agent 接单                   | **部分对齐**：端到端自动化 + 人机分工，但单 agent 为主 | A        |

一句话结论：**公开案例里，「真多智能体协作」目前集中在法律/专业服务这类高判断密度场景（案例 1）；建材与制造业的公开成果集中在「单点文档自动化」与「销售 copilot」（案例 2–5）。把两者拼成「多岗位 agent 协同 + 人在环审批 + 全程可追溯」的建材行业公开样本，本次未检索到。**

## 2. 案例详述

### 案例 1｜Harvey：把合同 playbook 审查重构成多智能体系统

- **主体**：Harvey（法律 AI 平台，服务律所与企业法务）。
- **场景**：企业收到对方合同后，法务需逐条对照公司 playbook（标准立场 / 可接受偏离 / 不可接受偏离 / 解释指引），标注风险并出修订建议（redline）。Harvey 引用 Gartner 数据称法务部门 21% 的产能花在合同事务上；单份合同审阅耗时 20 分钟到 5 小时。
- **做法**：
  1. 弃用「固定 prompt 流水线」（分类 → 检索 → 摘要 → 改写，各步独立），原因是上下文在调用间丢失、只能按条款局部改、多条规则会给出互相冲突的修改。
  2. 改为 **orchestrator + worker**：主办 agent 扮演「主办律师」拆活，为每条 playbook 规则起一个子 agent，**最多数十个并行**；子 agent 自己读规则、检索合同、判断是否合规、选择追标准立场还是某个 fallback、产出修订清单，并写一份短备忘录说明分类、改动与理由。
  3. **分支-合并**：每个子 agent 在自己的文档分支上改，改动以 tracked change 标注并打上规则标签；汇总时像版本控制一样合并，冲突升级给主办 agent 裁决。
  4. **上下文共享**：代表哪一方、用谁的模板、第几轮谈判、宽严尺度、先例文件，全层级 agent 都能看到。
  5. **状态持久化**：分类、所选立场、改动摘要、理由随审阅存档；用户追问或改选立场时复用相关 agent，不整链重跑。
  6. 规模化护栏：按模型/阶段/文档大小设超时与定向重试、并发上限与退避、prompt 前缀缓存、结果流式返回、按子任务选模型、多模型适配层。
- **公开披露效果**（自建评测集，LLM 评委 + 三个前沿模型投票）：

  | 指标           | 改造前   | 改造后   | 变化         |
  | -------------- | -------- | -------- | ------------ |
  | 风险分类准确率 | 59%      | 77%      | +18 个百分点 |
  | Redline 评分   | 53%      | 87%      | +34 个百分点 |
  | 平均时延       | 2.6 分钟 | 3.8 分钟 | +47%         |

  作者明确说明：质量换时延是**有意取舍**。

- **来源**：https://www.harvey.ai/blog/rebuilding-playbook-review-as-a-multi-agent-system
- **证据级别**：**C**。理由：工程团队一手复盘，给了架构、评测方法与前后对比，属最可信的技术证据；但评测集自建、指标自评、无第三方复核，且未披露客户侧上线数据。
- **对齐点**：
  - 岗位型分工（主办律师 / 协办律师）而非「一个万能 agent」，与「多智能体协作」的形态一致。
  - 有明确的**权限与升级机制**：冲突不由某个 agent 硬拗，而是升级到主办 agent 裁决；「有些决定不能下放」被写进设计。
  - 人在环是**结构性**的：agent 出首轮草案 + 理由 + 原文定位，律师做终审，而不是人给 agent 打下手。
  - 结论逐条挂原文位置（唯一 ID + 引用），天然可追溯、可审计。
- **不对齐点**：
  - 它是**法律专业工具内的单点流程**，不覆盖合同录入/OCR、客户资质、报价、履约、开票；不构成跨部门业务自动化。
  - 人只是「审阅者」，不是审批流中的权限节点（没有金额/账期分级授权、没有双人复核）。
  - 质量依赖自建 benchmark 与内部律师标注，这个前提在建材企业不存在。
  - 它不是「数字员工团队」：没有销售、商务、财务等岗位 agent 的协同。
- **可借用**：到件即触发、主办-协办分工、分支合并、冲突升级、逐条引用、状态复用。

### 案例 2｜Holcim：用生成式 AI 做发票分类与路由（Omnivore）

- **主体**：Holcim（全球建材集团，70+ 国家、63,448 名员工）。
- **场景**：应付发票量大、格式杂，人工分类与分派给对应团队耗时且易错。
- **做法**：内部团队基于 Amazon Bedrock 的大模型自建 **Omnivore**，自动完成发票的**分类与路由**；配套 AWS Skills Guild 做全员云与生成式 AI 能力建设（近 500 名 IT 员工、两年 50+ 场培训、100+ 云实践者）。
- **公开披露效果**：
  - 单一国家的发票人工处理量**减少 90%**，覆盖**约 2,000 张/月**。
  - 官方称处理成本显著下降、质量与时效提升；方案已准备向欧洲扩展。
  - 注：页面首屏另有一个「90%」出现在 benefits 区，指的是同一指标的重复呈现，不是两个独立成果。
- **来源**：https://aws.amazon.com/solutions/case-studies/holcim-case-study/
- **证据级别**：**B**。理由：AWS 官方客户案例，引用了 Holcim 全球 I&O 负责人与云架构负责人的署名原话，部署范围与口径写得较清楚；但由厂商制作，未披露准确率、返工率与成本基线。
- **对齐点**：
  - **同行业同构**：建材企业的单据流（发票、对账单、发货单）与合同附件高度相似，是「业务自动化」最容易出效益的切口。
  - 是**闭环**不是问答：识别 → 分类 → 路由到处理团队，有下游动作。
  - 由内部团队自建、可复制到其他国家，说明组织能力可沉淀。
- **不对齐点**：
  - **单模型流水线，不是多智能体**：没有多个岗位 agent 的分工、协商与冲突裁决。把它讲成「多智能体」是偷换概念。
  - 只做分类与路由，**不做条款判断**，也不进入审批链。
  - 「90%」是单一国家、单一流程的口径，不能线性外推到多语言、多税制、多业务单元。
- **可借用**：以「单据/合同附件」为第一个自动化切口；用「月处理量 × 人工降幅」作为 ROI 口径；先单国/单区域跑通再复制。

### 案例 3｜Schneider Electric：全球销售团队的 Copilot for Sales 与 CRM 回写

- **主体**：Schneider Electric（电气设备制造，B2B，10,000+ 员工）。
- **场景**：全球销售在多个系统间切换，手工做客户调研与 CRM 录入，挤压真正面对客户的时间；CRM 数据质量差。
- **做法**：
  - 将 Copilot for Sales 与 Salesforce CRM 打通，在 Outlook / Teams 内完成**联系人创建（AI 预填、销售只做校验保存）**、邮件与会议摘要、会议要点自动回写 CRM、报价材料要点改写。
  - 分十个部署区域，每区设一名 project champion / owner；总部给沟通素材与价值话术，但允许各区自行表达——因为各国销售流程与文化不同。
  - 先试点、持续收反馈、迭代推广。
- **公开披露效果**：
  - 上线时 **5,000 人、30+ 国家、5 种语言**在用；计划 2024 年底达到 **10,500 人**。
  - 联系人生成量相对基线「显著增长」（原文未给百分比）。
  - 销售反馈：每人每天最多 100 封邮件，摘要「节省了可观的行政时间」；会议纪要含下一步并自动进 CRM。
  - 均为定性或进度指标，**没有 win rate / 客单价 / 合同周期的硬数字**。
- **来源**：https://www.microsoft.com/en/customers/story/18860-schneider-electric-microsoft-365-copilot-for-sales
- **证据级别**：**B**。理由：Microsoft 官方客户故事，有 SVP、VP、销售工程师的署名原话与明确席位数；但由厂商编辑、无对照组、效果多为客户主观评价。
- **对齐点**：
  - **制造业 B2B、销售人数多、跨区域**——与本项目客户画像最接近的公开样本。
  - 关键不是「会聊天」，而是**把结果写回系统**（CRM 记录、会议纪要），形成数据闭环。
  - 推广方式可借鉴：区域 champion + 本地化话术，而不是总部一刀切。
- **不对齐点**：
  - **单点 copilot，不是多智能体**：没有 agent 之间的分工与交接。
  - 不碰合同条款、不碰报价审批、不做权限分级——离「业务自动化闭环」还有一段。
  - 效果披露以「省时间」为主，无法支撑收入类承诺。
- **可借用**：把销售助手嵌进销售已经在用的入口（邮件/企微/钉钉/CRM），而不是新开一个系统；以「每周节省小时数 + 数据回写完整率」作为一期验收指标。

### 案例 4｜KPN：销售赋能的可量化落地（78 人survey、RFP 摘要、报价草案）

- **主体**：KPN（荷兰电信与 ICT 服务商，1,000–9,999 人）。
- **场景**：销售周期 4–9 个月，营销与销售在 routine 任务上耗时多，线索质量与提案质量待提升。
- **做法**：
  - 2024 年 1 月以 **50 人**做 PoC，聚焦线索资格判定与商机情报；4 个月后扩到**再加 300 名销售**。
  - 用 Copilot for Sales 做：邮件/会议摘要、报价与提案草案、技术材料改写、**RFP 长文档摘要**、联系人/商机一键回写 Salesforce。
- **公开披露效果**：
  - **78 名销售**的调研：人均**每周节省近 2 小时**。
  - 内部调研：**69%** 的客户经理认为提案质量提升、赢单概率提高（是「认为」，不是实际赢单率）。
  - 销售自述：过去做一份销售活动表单要 4 小时，现在一键生成。
- **来源**：https://www.microsoft.com/en/customers/story/24202-kpn-microsoft-365-copilot-for-sales
- **证据级别**：**B**。理由：同上，有署名销售管理者原话与明确样本量（78 人）；但样本自选、无对照组，69% 是主观判断。
- **对齐点**：
  - 给出了**可复制的度量方式**：小样本问卷 + 单人周节省小时 + 提案质量主观评分，适合作为 POC 验收口径。
  - 「RFP/长文档摘要 → 报价草案」正是销售赋能里最贴近合同与投标的环节。
- **不对齐点**：
  - 纯辅助，**不闭环**：不自动生成正式报价、不走审批、不回写合同系统。
  - 没有多 agent 协作，也没有权限与审计设计。
  - 电信行业标品销售，与防水材料的工程定制、区域经销、账期返利差异大，不能直接套用其流程。
- **可借用**：POC 设计（50 人 → 300 人）、以「周节省小时」立项、以「提案/RFP 摘要」作为低风险高感知的第一个场景。

### 案例 5｜Salesforce Customer Zero：SDR agent 端到端跑线索

- **主体**：Salesforce（企业软件，自用其 Agentforce，称 Customer Zero）。
- **场景**：销售开发（SDR）大量时间花在冷线索培育、首轮触达与资格判定；客服大量重复咨询。
- **做法**：
  - 部署 SDR agent：自主潜客挖掘、外呼/邮件触达、答疑与异议处理、约会议，基于 CRM 与外部数据；复杂或高价值对话**移交给人类销售**并带摘要。
  - 客服 agent 承接帮助站点咨询，多数 case 无人工介入。
  - 明确的人机分工：agent 做「量大、重复、被拒绝也不疲劳」的活，人做关系与复杂成交。
  - 失败教训公开：早期 agent 回答「I don't know」的比例达 **30%**，靠数据治理（单一事实源、清理过期页面、合并 650+ 数据流）降到**10% 以下**；过度限制（竞品黑名单）反而误伤正常问题，改为给目标而非给死规则。
- **公开披露效果**（上线一年）：
  - SDR agent 处理 **43,000+ 条线索**，从沉睡线索中带来 **170 万美元**新管线。
  - 客服 agent 处理 **150 万+** 支持请求，多数无人工。
  - Slack 内 Agentforce 为团队省回 **50 万小时**；**86%** 员工在 Slack 用 agent，**99%** 全球员工使用内部 agent。
- **来源**：https://www.salesforce.com/news/stories/first-year-agentforce-customer-zero/
- **证据级别**：**A**。理由：当事企业官方新闻室自述，数字与失败教训都写得具体，可信度高于厂商客户故事；但仍是自我披露、无审计，且「自家产品自家用」存在强激励偏差。
- **对齐点**：
  - **端到端自动化 + 明确人机分工**：agent 跑到「约会议/移交」，人接高价值环节。
  - 承认「数据不统一 → agent 编答案」，把数据治理当成前置条件而非配套——这与企业级落地的真实约束一致。
  - 有可观测指标（处理量、管线、节省小时、使用率）。
- **不对齐点**：
  - **以单 agent 为主，不是多 agent 协作**；「多 agent」在这里更多是多个独立 agent 并存，不是围绕一个业务流程分工协同。
  - 是软件公司卖软件，流程标准化程度远高于建材制造与工程销售。
  - 43,000 线索 / 170 万美元是**其自有漏斗与客单价**下的结果，不可移植为本项目收益。
- **可借用**：先定「agent 做到哪一步、人在哪一步接」；把「不知道率」当作核心质量指标；数据治理先行。

## 3. 判别口径：哪些「案例」其实不算

方案里容易被拿来充数的三类，建议明确排除，避免叙事失真：

| 形状                          | 为什么不算「多智能体协作 + 业务自动化」                  | 可以怎么用                                               |
| ----------------------------- | -------------------------------------------------------- | -------------------------------------------------------- |
| 单点 RPA / 规则引擎           | 流程固定、无判断、无协商；只是把点击自动化               | 作为确定性环节的执行层（如盖章、归档、推送），不当作卖点 |
| 纯流程挖掘 / 任务看板         | 只观测不执行，不产生业务动作                             | 作为上线前的流程基线测量                                 |
| 纯聊天助手 / 知识问答         | 有问才答，不进流程、不写回系统、不担责                   | 作为员工入口，但必须挂到具体业务动作上才算闭环           |
| 「多个 agent 并存」但各干各的 | 没有共享上下文、没有交接与冲突裁决，只是产品里有多个 bot | 只能叫「多助手」，不能叫「多智能体协作」                 |

判断一条案例是否真对齐，问四个问题：

1. 是否有**两个以上岗位角色**的 agent 围绕同一业务目标分工？
2. 是否有**交接物**（结构化结论 + 原文依据）在 agent 之间传递？
3. 是否有**冲突/例外升级**机制，且最终由人拍板？
4. 是否**写回业务系统**并留下可追溯记录？

四问全「是」才是强对齐；只有 1–2 个「是」，只能算部分对齐。

### 5.3 不可直接照搬

1. **不能把 Harvey 的质量数字当作本项目预期**。77%/87% 来自其自建评测集与内部律师团队标注；防水企业没有等价 benchmark，必须先建 100–200 份历史合同的标注集（此数量为建议假设，需与法务确认）。
2. **不能把「法务轻触修改」标准套到销售报价**。合同审阅追求最小改动，报价与方案追求说服力，二者的质量函数相反。
3. **强规则不能交给 LLM 自由裁量**。经销返利、账期授信、区域价格政策应走规则引擎/额度表，agent 只做解释、取数与异常提示；否则不可审计。
4. **不能把 Salesforce 的 43,000 线索 / 170 万美元管线当作可复制收益**。那是软件公司自有漏斗与客单价，行业、客单、转化路径完全不同。
5. **Holcim 的 90% 不能线性外推**。口径是「单一国家、约 2,000 张/月、单一流程」；多语言、多税制、多法人会显著抬高复杂度。
6. **大规模席位推广不是技术问题**。Schneider 从 5,000 到 10,500 人靠的是十区 champion 与持续 change management，这部分工作量不应被低估。
7. **不要把「多个 agent」当卖点**。若没有共享上下文、交接物、冲突升级与写回系统，只是多个 bot，反而会在评审中被质疑。

## 6. 对方案设计的三条硬约束（来自案例的反向教训）

1. **数据一致性优先于模型能力**（案例 5）：agent 遇到两个「都对」的答案会自己编一个。合同模板库、价格政策、客户资质必须单一事实源，否则多智能体只会把错误放大到更多环节。
2. **质量与时延要显式取舍**（案例 1）：多 agent 并行会把时延抬高（2.6 → 3.8 分钟，+47%）。方案应写明「首轮结论几分钟内出、全量审阅多久」，而不是承诺又快又准。
3. **人审要设计成「例外处理」而不是「全量兜底」**（案例 1 / 5）：如果人要把 agent 的每条结论都重看一遍，自动化收益归零；必须定义分级授权与抽检比例。
