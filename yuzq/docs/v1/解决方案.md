# 解决方案：雨中情防水技术集团

## 面向企业的多智能体协作，在运行时上把业务自动做起来

> **一句话**：面向企业的多智能体协作，在运行时上把业务自动做起来（面向企业 · 多智能体协作 · 业务自动化）。
>
> **在本客户的落地含义**：把"合同到件 → 结构化 → 首轮审查 → 派单"和"标书/讲标素材"这两段业务，拆成有名字、有边界、有交接物的岗位，由 agent 在运行时按规则协作完成；法务、录入、销售在关键节点审批与定稿；每一步都能事后查到。
>
> **文档性质**：内部方案稿，供客户沟通前的人工评审使用。效益数字全部为**假设**，不是预测、不是承诺、不是已验证 ROI。本文不声称 Agent Forge 与雨中情防水技术集团存在任何合作、签约或交付关系。

---

## 0. 先回答四个问题

方案的价值主张只有一句：**面向企业的多智能体协作，在运行时上把业务自动做起来**。落到这家企业，需要先把这句话翻译成"谁干活、谁批、怎么验"。

### 0.1 哪些业务、哪些岗位、谁审批、如何验收

| 业务                             | 由哪些岗位型 agent 协作完成                                                            | 协作模式                                              | 人（审批 / 定稿）                                | 验收人与验收方式                                       |
| -------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------ |
| 合同到件 → 结构化 → 待审队列     | 合同收件员 → 抽取员 → 字段校验员 → 缺件催办员                                          | **pipeline**：串行、互相不信任、以原件为唯一依据      | 录入岗确认差异清单与低置信字段后才入队           | 法务/商务抽样对原件复核；**静默错误必须为 0**          |
| 合同首轮条款审查                 | 合同主办（supervisor）+ 商务条款审阅员、质保条款审阅员、资质合规审阅员、用印要件审阅员 | **supervisor**：主办拆活分派、子 agent 并行、冲突升级 | **法务终审人签发结论**；例外与偏离由法务负责人批 | 法务按标注集评采纳率与漏报；每条结论必须能回到原文位置 |
| 合同流转派单                     | 流转派单员                                                                             | 附属于上两段                                          | 法务/商务确认派单对象与时限                      | 派单准确率、超时率                                     |
| 标书 / 讲标素材                  | 招标解析员 → 业绩匹配员 → 技术段落撰稿员 → 商务偏离核对员 → 一致性校验员               | **pipeline + 校验闸门**                               | **销售本人定稿与讲标**，区域负责人复核           | 销售管理部评可用段落率、制作工时、虚构业绩拦截         |
| 销售政策问答（可选，非本次 POC） | 政策检索员                                                                             | 单角色问答                                            | 销售管理/商务保留解释权与例外批准权              | 引用原文率、不知道率（不达标不扩量）                   |

### 0.2 三条判断

1. **合同链路是主战场。** 它是上游唯一同时满足"多岗位分工、有交接物、冲突由人裁决、写回留痕"四个条件的场景（痛点分析 §1 P2、§2.1），因此多智能体的协作价值在这里最实。
2. **销售赋能写"供料"，不写"替代"。** 标书与讲标素材可以多角色协同，业绩资质不得由 agent 生成，报价与让利不进 agent（痛点分析 §1 P6、P8）。
3. **不碰的四件事**：出具法律意见与认定责任、用印批准与授权授予、最终报价与让利、经销返利/账期授信测算（痛点分析 §2.3）。这不是保守，是这类业务的质量函数与法律责任都不允许模型定夺。

> 边界提醒：上游明确"多智能体协作 + 人在环审批 + 全程可追溯"的建材行业公开样本**本次未检索到**（痛点分析 §2.4）。所以本方案是**形状推理**，不是"同行已验证"的复制。对外沟通不得包装成行业已验证。

## 1. 为什么从这两段业务切入

### 1.1 两个场景的性质不同，方案不能一套打法

| 维度     | 合同链路（P1/P2/P3/P4）               | 销售赋能（P6/P7）                | 报价让利（P8）                   |
| -------- | ------------------------------------- | -------------------------------- | -------------------------------- |
| 判断标准 | 可外化为 playbook、要件清单、字段口径 | 部分可外化（评分办法、政策原文） | 不可外化（竞争、关系、战略取舍） |
| 对错     | 有唯一答案（以原件、以规则为准）      | 有事实错误但无唯一最优           | 无客观对错，只有盈亏后果         |
| 适配结论 | **强对齐**                            | **部分适合**：供料 + 校验        | **不宜硬上**                     |

### 1.2 先修进料口，再修判断口

合同以照片、扫描件形式到件、需人工录入后才能进入审查，这是**结构性**问题而非偶发：多基地、42 个办事处、500 多家服务网点（痛点分析 §1 P1 引客户画像），到件来源分散、拍摄质量不一。不解决进料口，审查 agent 拿不到可用输入；但进料口单独看价值有限，所以与审查同批推进、以审查为主叙事（痛点分析 §3.2）。

### 1.3 系统依赖度决定了推进顺序

合同链路可以落在"文件 + 审批流"上；销售链路要求 CRM 回写，而客户是否存在 CRM、ERP、合同系统、电子签、OCR **均未检索到公开来源**（痛点分析 §1 P9）。因此在系统清单确认前，合同链路是风险更低的起点。

> 2018 年泛微协同 OA 是否仍在用、覆盖哪些审批流，上游为二手信息且待核（痛点分析 §1 P3）。本方案一律按"可能已有审批流"处理：**只叠加，不替换**。

## 2. 总体架构：多智能体怎么把业务做起来

### 2.1 全景

```
【合同链路】
邮箱/共享目录到件
      │（事件触发）
      ▼
合同收件员 ──缺件──▶ 缺件催办员 ──▶ 回到到件
      │ 完整性清单 + 原件索引
      ▼
  抽取员（原件 → 字段 + 原文位置 + 置信度）
      │ 结构化结果
      ▼
 字段校验员（对齐主数据与字段口径）
      │ 差异清单（低置信标黄）
      ▼
  ★ HITL-1 录入岗确认差异 ──▶ 待审队列
      │
      ▼
 合同主办（supervisor）：读 playbook，拆条款、派活
      ├──▶ 商务条款审阅员 ─┐
      ├──▶ 质保条款审阅员 ─┤  各自输出：
      ├──▶ 资质合规审阅员 ─┤  偏离项 + 原文位置 + 规则编号 + 建议 + 置信度
      └──▶ 用印要件审阅员 ─┘
      │ 汇总；子 agent 结论冲突 → 主办不折中，升级
      ▼
  ★ HITL-2 法务终审人签发；HITL-3 例外/偏离批准
      │
      ▼
 流转派单员 ──▶ ★ HITL-5 派单确认 ──▶ 写回（文件 / OA 待审状态）

【销售赋能链路】
招标文件/评分办法
      ▼
招标解析员 → 业绩匹配员（只读案例库）→ 技术段落撰稿员 → 商务偏离核对员
      ▼
一致性校验员（禁虚构业绩、禁超授权承诺、口径统一）
      ▼
  ★ HITL-6 销售定稿与讲标（agent 只供料）
```

### 2.2 合同链路：岗位、输入输出与交接物

| 岗位型 agent           | 输入                       | 输出 / 交接物                        | 依据的规则                            | 不确定时怎么办                                |
| ---------------------- | -------------------------- | ------------------------------------ | ------------------------------------- | --------------------------------------------- |
| 合同收件员             | 到件（照片/扫描件 + 附件） | 收件登记、完整性清单、原件索引       | 合同类型与附件要件清单                | 缺页/缺附件/骑缝章遮挡 → 转催办，**不进抽取** |
| 抽取员                 | 原件                       | 字段值 + 每字段原文位置 + 置信度     | 字段字典                              | 低置信**标黄**，禁止静默补全                  |
| 字段校验员             | 结构化结果 + 原件 + 主数据 | 差异清单、归一结果                   | 含税/不含税、甲方全称、账期、账户口径 | 三方不一致 → 升级人工，不自行折中             |
| 缺件催办员             | 完整性清单                 | 催办任务与回执                       | 时限规则                              | 超时 → 通知责任人                             |
| 合同主办（supervisor） | 校验后合同 + playbook      | 审查计划、汇总结论、冲突清单         | playbook 版本号                       | 冲突不裁决法律定性，升级法务                  |
| 商务条款审阅员         | 条款切片 + playbook        | 付款/账期/违约/结算偏离项            | 商务条款规则                          | 规则未覆盖 → 标"未覆盖"，不猜                 |
| 质保条款审阅员         | 条款切片 + playbook        | 质保期/质保金/响应时限偏离项         | 质保条款规则                          | 同上                                          |
| 资质合规审阅员         | 签约主体、资质要件         | 主体与资质要件核对结果               | 主体选择规则、资质清单                | 规则缺失 → 挂起等人工                         |
| 用印要件审阅员         | 用印要件材料               | 要件齐备性结论（**不判断能否盖**）   | 用印要件清单                          | 缺件 → 退回                                   |
| 流转派单员             | 审查结论                   | 待审队列条目、派单建议、写回 payload | 派单规则与时限                        | 无匹配承接人 → 人工指派                       |

**交接物的设计原则**：每个岗位只交"下一个岗位能独立校验的东西"——原件索引、字段 + 位置 + 置信度、偏离项 + 规则编号。没有交接物的多 agent 只是多个 bot，上游已明确排除这种空壳编排（痛点分析 §2.3）。

### 2.3 两种协作模式，各有各的用处

| 模式                                  | 用在哪             | 为什么                                   | 关键约束                               |
| ------------------------------------- | ------------------ | ---------------------------------------- | -------------------------------------- |
| **pipeline**（串行）                  | 到件 → 抽取 → 校验 | 单一路径、错误可定位、可对原件验证       | 上下游互不信任；下游必须能独立回查原件 |
| **supervisor**（主办 + 并行子 agent） | 首轮条款审查       | 条款可按专业切分，冲突需要有人汇总后升级 | 主办只汇总不折中；冲突一律给法务终审人 |
| **pipeline + 校验闸门**               | 标书素材           | 生产可并行，但一致性必须单点把关         | 校验不通过不交付，不允许"先发再改"     |

上游案例 1（Harvey，C 级）的形状是"主办拆活 + 按 playbook 并行 + 冲突升级 + 结论挂原文"，本方案借用的是这个**形状**，不借用其任何效果数字；其对外引用的效率提升比例依赖自建评测集与内部律师标注，该前提在本客户不存在（痛点分析 §1 P2）。

### 2.4 HITL 落点：人批什么、在哪批、不批会怎样

| 编号   | 审批动作             | 审批人                   | 批的是什么                   | 落点            | 默认行为         |
| ------ | -------------------- | ------------------------ | ---------------------------- | --------------- | ---------------- |
| HITL-1 | 差异与低置信字段确认 | 录入岗                   | 改哪几个字段、依据哪一处原件 | 复核台          | 未确认不入队     |
| HITL-2 | 首轮审查结论签发     | 法务终审人               | 结论是否成立、哪些需人工重审 | 法务工作台      | 未签发不派单     |
| HITL-3 | 例外与偏离批准       | 法务负责人（按授权层级） | 让到什么程度、依据哪条例外   | 审批流          | 未批按红线处理   |
| HITL-4 | 用印批准与授权授予   | 印章管理员 / 授权人      | 能不能盖、谁有权签           | 既有 OA（待核） | 不进 agent 决策  |
| HITL-5 | 派单确认             | 法务/商务                | 派给谁、什么时限             | 待审队列        | 无确认不写回     |
| HITL-6 | 标书定稿与讲标       | 销售本人 / 区域负责人    | 对外口径与承诺               | 文件定稿        | agent 输出仅素材 |
| HITL-7 | playbook 变更        | 法务负责人               | 规则改了什么、影响哪些条款   | 规则库          | 未批准不生效     |

> **企业版相关**：HITL-2/3/5 属于"由他人审批"，若要求审批人与发起人严格分离、并把审批结果作为独立存证，对应平台**企业版**能力（他人 HITL、审计验真）。多法人主体若要按主体隔离写入，对应**多租户写**，同样属企业版。社区版可自托管跑通单主体、单角色链路（如 POC-1）；POC-2 的跨人签发需企业版。

### 2.5 系统集成点：先只读接入，写回单点可控

| 集成点                      | 方向      | 说明                                               | 状态         |
| --------------------------- | --------- | -------------------------------------------------- | ------------ |
| 到件入口（邮箱 / 共享目录） | 只读      | 事件触发，不改动原邮件与目录                       | 待客户确认   |
| 文件存储                    | 读写      | 原件、结构化结果、差异清单、回放记录统一存放       | 自托管       |
| OCR / 版式识别              | 调用      | 是否已有工具未知，不预设选型                       | **待核 6**   |
| 待审队列 / 审批流           | 写回      | 优先叠加既有 OA（2018 泛微，待核 5），不新建审批链 | **待核 4/5** |
| 主数据（客户、主体、账户）  | 只读      | 字段校验的比对基准；来源未知                       | **待核 4**   |
| 标书库 / 案例库             | 只读      | 若不存在需先建最小库，工作量常被低估               | **待核 15**  |
| CRM                         | 只读/写回 | 是否存在未知，销售侧写回可能无处可写               | **待核 4**   |

**写回纪律**：只写"待审/草稿"状态，不直接写终态；写回幂等、可撤销、带操作人；每次写回都在观测里留下 payload 与返回。

## 3. 怎么工作：造、跑、治理、观测

> 本节是**能力清单与工作方式**，不是对外主叙事。对外仍然只有一句话：面向企业的多智能体协作，在运行时上把业务自动做起来。

### 3.1 造：把业务配成岗位

把一个业务环节变成岗位，要写清四件事：**角色、能力、触发器、会话**。

- **角色**：岗位名、职责边界（尤其是"不做什么"）、上下游、升级条件、审批人。例如"用印要件审阅员"的角色卡里必须写明：只核对要件齐备性，不判断能否用印。
- **能力**：这个岗位被允许调用的工具与知识（playbook 片段、字段字典、要件清单）。能力是白名单，不是"什么都能干"。
- **触发器**：到件事件（新合同进入）、定时（每日待审队列巡检、超时催办）、人工发起（会话里点单）。触发器决定"业务是自己往前走，还是等人推"。
- **会话**：一案一会话。交接物作为上下文挂载，跨案件不串；同一合同的历次修订共享一条上下文线，避免"换个 agent 就重新问一遍"。

**造的重点不是提示词，是把规则外化。** 上游已明确：没有 playbook 与标注集，并行 agent 只会把口径分歧放大到更多条款（痛点分析 §1 P2）。所以"造"的第一步是跟法务共建 playbook，而不是先配 agent。

### 3.2 跑：运行时 + MCP / Skill

- **运行时**负责把岗位跑起来：按触发器启动、按依赖调度、在 HITL 节点挂起等审批、审批后继续、失败重试、超时升级。
- **MCP** 接系统：文件、OCR、OA 审批流、主数据、案例库。接口能力决定"能不能写回"，这也是为什么系统清单是阻塞项。
- **Skill** 封装业务规则：playbook 检查、字段口径、要件清单、评分办法拆解。规则改动走 Skill 版本，而不是改一堆散落的提示词。
- **执行纪律**：工具白名单 + 最小权限；只读与写入分离；写操作必须带审批凭据；长任务可见进度，不做黑箱等待。

### 3.3 治理：把权限事先定好

| 治理项           | 做法                                                          | 在本客户的具体落点                           |
| ---------------- | ------------------------------------------------------------- | -------------------------------------------- |
| **权限事先定好** | 角色 × 工具 × 数据范围三元组，先定义再上岗                    | 按法人主体划数据范围；法务只看授权主体合同   |
| **审批 / HITL**  | 审批是运行时的一等状态，不是事后补签                          | 2.4 的 7 个落点                              |
| **审计**         | 谁、何时、对哪版规则、批了什么，独立留存                      | 法务签发、例外批准、用印、写回               |
| **熔断**         | 按主体 / 按合同类型 / 全局三级停                              | 出现静默错误、采纳率连续不达标、时延超阈即停 |
| **RBAC**         | 录入岗、法务、法务负责人、销售、销售管理、IT 管理员、审计只读 | 审计只读不得改数据；IT 不得代法务签发        |

**Open-Core 与部署形态**：

- **社区版可自托管**，适合在客户环境内跑通单主体、单角色链路（如 POC-1 的抽取与校验）；涉及法务终审等跨人审批时需企业版。
- **企业版钥匙**解锁多租户写、他人 HITL、审计验真等能力。本客户是多法人结构（痛点分析 §1 P3），一旦要求"按主体隔离 + 跨人审批 + 审批可验真"，就需要企业版，这一点应在报价与排期前讲清，避免 POC 后被能力边界卡住。
- **部署形态建议自托管**：合同原文、客户名单、价格、账期不出客户环境。是否允许调用外部模型，取决于待核 17（数据安全/等保/信创要求），**未答之前不做架构承诺**。

### 3.4 观测：做完能查到每一步

观测不是"看个仪表盘"，而是任何一份合同都能回答：**它为什么被这么判、谁批的、依据哪版规则、花了多久**。

| 可查项     | 内容                                           |
| ---------- | ---------------------------------------------- |
| 触发       | 何时、从哪个入口、由谁/什么事件触发            |
| 角色链     | 经过了哪些岗位，每个岗位的输入输出与交接物版本 |
| 工具调用   | 调了什么、返回什么、失败重试几次               |
| 审批       | 审批人、审批时间、批的是哪一版结论、批注       |
| 写回       | 写到哪个系统、payload、返回结果、是否可撤销    |
| 成本与时长 | 每个岗位耗时、端到端时延、模型/OCR 调用量      |

**观测与审计的分工**：观测面向运营改进（哪里慢、哪里改判多、哪里总升级），审计面向合规存证（不可篡改、可验真）。两者同源不同权限：业务看观测，内控与审计看存证。

**运营指标**（POC 期间就要采集，作为扩量依据）：处理量、端到端时延 P50/P90、人工改判率、冲突升级率、法务采纳率、静默错误数、不知道率（若做政策问答）。

## 4. POC 切口：三个小而可验收的场景

> POC 原则：单主体、单合同类型、有金标、有对照基线、有人签字。**不追求覆盖全集团，追求"这一段真的能自动跑起来且有人敢用"。**
>
> 下文的周期与阈值均为**规划假设**，须在启动会与客户共同确认后写入验收单，不作为交付承诺。

### POC-1｜合同到件 → 结构化 → 差异清单

| 项                   | 内容                                                                                                                                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **范围**             | 单一法人主体、1 类高频合同（建议项目合同）；照片/扫描件到件 → 字段抽取 → 交叉校验 → 差异清单 → 人工确认 → 待审队列。**不含**用印、不含对外发送、不做零人工入库                                                    |
| **参与角色**         | 合同收件员、抽取员、字段校验员、缺件催办员（pipeline）                                                                                                                                                            |
| **系统集成点**       | 只读到件目录/邮箱；OCR（选型待核）；复核台；待审队列（先落文件目录，再对接 OA）                                                                                                                                   |
| **验收指标**         | ① 高后果字段（金额、主体、账户、账期）与人工复核一致率；② **静默错误数 = 0**（未标黄即写入且与原件不符）；③ 单份人工复核耗时相对基线下降；④ 到件→入队端到端时延；⑤ 标黄字段人工改判率（用于校准阈值，不设达标线） |
| **建议阈值（假设）** | 一致率 ≥98%、人工复核耗时下降 ≥50%、静默错误 0。阈值须先测基线再定，基线未知时不得先承诺                                                                                                                          |
| **周期**             | 4–6 周（含 1 周基线测量）                                                                                                                                                                                         |
| **前置条件**         | 待核 1（合同量与扫描件占比）、4（系统清单）、6（是否已有 OCR/CLM）、17（合规）；测试样本 50–100 份；指定金标标注人                                                                                                |
| **明确不做**         | 零人工全自动入库；低置信字段自动补全；跨主体批量处理                                                                                                                                                              |

**为什么先做它**：正确性可对原件验证，不依赖 CRM，且它是 POC-2 的输入契约。

### POC-2｜合同首轮审查 + 留痕

| 项                   | 内容                                                                                                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **范围**             | 单一主体、2–3 类高频合同（建议）；输出"偏离项 + 原文位置 + 规则编号 + 建议 + 置信度"，供法务终审。**不出法律意见、不做定责、不碰用印批准**                                                    |
| **参与角色**         | 合同主办（supervisor）+ 商务条款、质保条款、资质合规、用印要件 4 个审阅员 + 流转派单员                                                                                                        |
| **系统集成点**       | playbook 库（与法务共建、版本化）；模板库；审查结果写回（文件 / OA 待审状态）；法务工作台（HITL-2/3）                                                                                         |
| **验收指标**         | ① playbook 要求条款的覆盖率；② 结论可回溯原文比例（**硬指标 100%**）；③ 法务采纳率（逐条标记采纳/不采纳）；④ 法务标注红线条款的漏检率；⑤ 冲突升级率与升级处理时长；⑥ 法务单份首轮耗时相对基线 |
| **建议阈值（假设）** | 覆盖率 ≥90%、采纳率 ≥70%、漏检率 ≤5%、首轮耗时下降 20%–30%（区间假设）。均须以标注集实测校准                                                                                                  |
| **周期**             | 6–8 周（playbook 共建可与 POC-1 并行启动）                                                                                                                                                    |
| **前置条件**         | 待核 2（审核时长/驳回率/层级）、3（法务人数与模板数）、7（playbook 是否存在）；100–200 份历史合同标注集（**建议数量，须法务确认**）；法务负责人签字确认规则口径与终审人                       |
| **明确不做**         | 法律意见、责任认定、例外自动批准、用印决定                                                                                                                                                    |

**为什么它是主叙事**：这是唯一"四问全过"的场景，也是多智能体协作真正产生交接价值的地方——单 agent 做不了"商务 / 质保 / 资质 / 用印"四种专业视角，而 supervisor 模式能让冲突显性化并交给人。

### POC-3｜标书 / 讲标素材供料

| 项                   | 内容                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **范围**             | 招标文件解析 → 评分办法拆解 → 业绩与资质匹配（只读库） → 技术段落初稿 → 商务偏离核对 → 一致性校验。**不含**业绩/资质生成、不含报价与让利、不直接对外发送    |
| **参与角色**         | 招标解析员、业绩匹配员、技术段落撰稿员、商务偏离核对员、一致性校验员（pipeline + 校验闸门）                                                                 |
| **系统集成点**       | 标书库/案例库（若无，先建最小可用库）；产品线资料；对外口径表（含"7 大工厂 vs 6 个基地"待核项）                                                             |
| **验收指标**         | ① 评分办法条目覆盖率；② 素材引用可溯源率（**硬指标 100%**）；③ 虚构业绩拦截（红队测试，放行数 = 0）；④ 初稿可用段落率；⑤ 单份制作工时相对基线；⑥ 销售采纳率 |
| **建议阈值（假设）** | 覆盖率 ≥85%、可用段落率 ≥60%、工时下降 ≥30%、虚构业绩放行 0                                                                                                 |
| **周期**             | 6–8 周；若需从零建库，追加 2–4 周（建议预留）                                                                                                               |
| **前置条件**         | 待核 10（销售人数与分布）、13（标书量与工时）、15（是否已有标书/案例库）、21（基地数量口径）                                                                |
| **明确不做**         | 生成或推断业绩、资质、荣誉；报价与让利；替代讲标                                                                                                            |

**为什么放在第三**：它直连订单、价值高，但素材库若不存在，前置工作量最容易被低估（痛点分析 §3.1）。且它依赖销售侧 champion，不适合作为第一个切口。

### 4.4 三个 POC 的关系与排期

```
阶段 0  摸底（2 周）：5 个阻塞项 + 系统清单 + 样本抽取 + 基线测量
   │
   ├─ POC-1（4–6 周）── 输出契约稳定后 ──▶ POC-2（6–8 周）
   │
   └─ POC-3（6–8 周，可与 POC-2 并行，需销售侧 champion 到位）
```

合计 12–16 周（**排期假设**，不含客户侧决策与采购周期；表中"扩量决策"的 2 周另计）。

**POC-1 与 POC-2 必须串行**：审查 agent 的输入质量取决于结构化契约；并行会导致 POC-2 用脏数据验证，结论不可信。**POC-3 可独立**，因为它不依赖合同链路。

### 4.5 三个 POC 都不做的事

- 不做报价、让利、返利、账期授信的自动决策（规则引擎范畴，且客户是否有经销体系尚未确认）
- 不做法律意见、责任认定、用印批准
- 不做 CRM/ERP 替换或重系统建设
- 不做"零人工"承诺
- 不对外自动发送任何文件

## 5. 效益假设：全部是假设，不是承诺

> **本节所有数字都是测算假设与算术示例**，没有一条来自客户实测，也没有一条可对外作为收益承诺。真实值取决于待核 1/2/10/13。POC 的第一件事是测基线，不是证明收益。

### 5.1 测算原则

1. 以"每 100 份合同"为单位测算，避免依赖未知的年合同量。
2. 每个假设单列，写明性质、依据、若不成立的后果。
3. 毛节省必须扣掉复核、集成、维护、变更管理成本，才谈净效益。
4. **不引用任何行业案例的百分比**，包括上游案例 1 的效率提升比例（其前提是自建评测集与内部律师标注，本客户不存在）。

### 5.2 假设台账

| 编号 | 假设                                               | 性质         | 依据 / 来源                       | 若不成立的后果                 |
| ---- | -------------------------------------------------- | ------------ | --------------------------------- | ------------------------------ |
| H1   | 每 100 份合同中 80 份为照片/扫描件、需人工录入     | **占位假设** | 上游无扫描件占比数据（待核 1）    | 录入环节收益按比例缩水         |
| H2   | 人工录入 + 自查 35 分钟/份                         | **占位假设** | 无客户基线，仅用于测算结构        | 节省绝对量变化，方向不变       |
| H3   | agent 出结果 + 人校差异 12 分钟/份（含低置信复核） | **占位假设** | 依赖 POC-1 实测                   | 若接近 H2，则该环节无收益      |
| H4   | 法务首轮审阅 90 分钟/份                            | **占位假设** | 上游明确法务时长未覆盖（待核 2）  | 审查环节收益无法估算           |
| H5   | 引入 agent 后 70 分钟/份（-22%）                   | **占位假设** | 无任何实测或行业数据支持          | 若法务仍需全量重审，收益趋近 0 |
| H6   | 标书 3 人日/份、年 20 份                           | **占位假设** | 上游无标书量与工时数据（待核 13） | POC-3 价值判断失效             |
| H7   | 引入 agent 后 2 人日/份                            | **占位假设** | 无实测                            | 同上                           |
| H8   | 综合人日成本 800 元                                | **占位假设** | 仅用于内部算术，非客户薪酬数据    | 金额换算变化，工时结论不变     |
| H9   | 复核 + 集成 + 维护成本按毛节省的 40% 预留          | **占位假设** | 行业经验值，无来源                | 净效益可能为负                 |

### 5.3 算术示例（把假设代入公式，不是预测）

**每 100 份合同：**

- 录入环节：`(35 − 12) 分钟 × 80 份 = 1,840 分钟 ≈ 30.7 小时`
- 审查环节：`(90 − 70) 分钟 × 100 份 = 2,000 分钟 ≈ 33.3 小时`
- 合计毛节省：`≈ 64 小时 ≈ 8 人日`
- 按 H8 折算：`8 × 800 = 6,400 元 / 百份（毛）`
- 扣 H9 后：`6,400 × 60% ≈ 3,840 元 / 百份（净，纯算术示例）`

**标书（按年 20 份）：**

- `20 份 × 1 人日 × 800 元 = 16,000 元 / 年（毛）`

**必须同时说清的三件事：**

1. 这些数字小得不足以支撑"降本"叙事——**这正是本方案不把降本当卖点的原因**。
2. 未计入 OCR 失败回退、缺件催办、法务返工、集成与运维人力；实际净效益可能显著低于示例，甚至为负。
3. 并行 agent 会抬高时延（上游案例已提示这一取舍，其数字属他人场景，**不作本客户预期**），若业务按"快"验收，需先对齐"首轮几分钟出"与"全量多久"两个口径。

### 5.4 真正的价值在非财务侧

| 价值       | 说明                                         | 可验证方式                       |
| ---------- | -------------------------------------------- | -------------------------------- |
| 留痕可回溯 | 每条结论挂原文位置与规则编号，被追问时能自证 | 随机抽 20 条结论，全部可回到原文 |
| 口径统一   | playbook 单点维护，多主体不再各判各的        | 同一合同跨主体复判一致性         |
| 风险前置   | 红线条款与缺件在进审前暴露                   | 缺件退回率、红线识别时点前移     |
| 新人上手   | 岗位化交接物即培训材料                       | 新人独立处理首份合同的时长       |
| 审计应对   | 审批链与规则版本可查                         | 审计抽样一次通过率               |

**结论口径**：POC 的验收应看"质量 + 可追溯 + 采纳率"，而不是"省了多少钱"。效益数字只在内部测算使用，对外一律标注假设。

### 6.2 模型误判的兜底：四道闸

1. **字段级**：低置信标黄 + 高后果字段双人复核，未确认不流转。
2. **角色级**：抽取与校验互不信任；条款官之间结论冲突由主办汇总、法务裁决，不允许模型折中。
3. **流程级**：写回只写"待审/草稿"，不写终态；任何结论都可退回人工全流程。
4. **运行级**：静默错误 ≥1、采纳率连续低于阈值、时延超阈 → 自动熔断该主体/该合同类型，转人工。

### 6.3 变更与回滚

| 变更对象         | 变更流程                                            | 回滚方式                               |
| ---------------- | --------------------------------------------------- | -------------------------------------- |
| playbook / 规则  | 法务签字 → 版本号 → 灰度 10% 合同 → 观测对比 → 全量 | 切回上一版本，历史结论保留原版本号     |
| 角色卡 / 提示词  | 变更评审 → 影子运行（只记录不写回）→ 小流量         | 回切旧角色卡                           |
| OCR / 模型供应商 | 影子运行比对 → 差异分析 → 灰度                      | 回切原供应商，原件与中间结果保留可重放 |
| 集成接口         | 只读先行 → 写回灰度 → 幂等校验                      | 关闭写回，退回文件流转                 |
| 紧急情况         | 三级熔断（主体 / 合同类型 / 全局）                  | 一键停用，人工全流程接管，事后复盘     |

**回滚的底线**：任何时点停掉 agent，业务必须能按原人工流程继续跑。做不到这一点的设计，不允许上线。
