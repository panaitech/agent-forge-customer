## 0. 结论速览

### 0.1 一句话

两个已知场景的痛点**性质不同**：合同链路是「有明确对错、有原文可依、必须留痕」的**高适配**场景，可拆成多岗位 agent 分工并由法务终审；销售赋能是「判断密度高、说服力导向、成败在人」的**部分适配**场景，宜做「初稿 + 提示 + 取数」，不宜让 agent 定夺报价与让利。

## 1. 客户侧痛点清单

### A 组｜场景一：合同照片/扫描件 → 录入 → 法务审查流转

#### P1 到件形态是「照片/扫描件」，结构化录入靠人

- **现状**：【场景前提】销售侧合同以照片、扫描件形式进入流程，需人工录入关键字段后才能进入审查与后续流转。【推断】结合该公司官网基地页列出的 6 个基地（另有"7 大工厂"口径待核，见 §1.3 第 59 行）、42 个办事处、500 多家服务网点（`客户画像.md` §0 情报卡第 21–22 行；§1.3 第 46–55 行）与"集团—区域子公司—办事处—服务网点"四层结构（§2.1 第 83 行），到件来源分散、拍摄质量不一，是**结构性**而非偶发问题。
- **为何难**：①照片存在倾斜、反光、缺页、骑缝章遮挡；②合同附件（报价单、技术协议、资质文件）常与主合同分离；③字段口径不统一（甲方全称、项目名、金额含税/不含税、账期表述），导致"抽出来也对不上"。上游已明确：是否已使用合同管理系统（CLM）、电子签章或 OCR 审阅工具**均未检索到公开来源**（§5.1 第 183 行），因此现状基线不可假设。
- **谁痛**：商务/内勤录入岗最痛（重复劳动）；法务次痛（拿到的是错字段，要回头核）；财务与用印岗连带（金额、账户、主体错误会传导到开票与盖章）。
- **能否拆成多智能体岗位协作**：**可以**。可按"收件与完整性检查 → OCR/版式抽取 → 字段归一与交叉校验 → 缺件回退催办 → 写入待审队列"分工，抽取 agent 与校验 agent 相互不信任、以原件为唯一依据。对照 `行业案例.md` 案例 2（Holcim 发票分类路由，B 级）：同属"单据识别 → 分类 → 路由"的闭环形状，但该案例**明确不是多智能体**（§2 案例 2「不对齐点」第 92–94 行），只能借"到件即触发 + 单区域先跑通 + 以月处理量作 ROI 口径"（§5.1 第 222–223 行），不能借其数字。
- **不宜硬上的边界**：**不建议做"零人工全自动入库"**。OCR 准确率在上游无任何数据（§5.1 第 183 行），而合同金额、主体、账号属高后果字段；正确形态是"agent 出结构化结果 + 差异清单，人只校差异"。低置信字段必须显式标黄，不得静默补全。
- **依据**：`客户画像.md` §0（第 21–22 行，渠道规模）、§1.3（第 46–55 行，基地）、§2.1（第 83 行，四层结构【推断】）、§5.1（第 183 行，CLM/OCR/电子签未覆盖）；`行业案例.md` §2 案例 2（第 77–96 行）、§5.1（第 222–223 行）。

#### P2 合同评审负荷上升，但法务产能基线完全未知

- **现状**：【推断】下游资金面收紧直接推高合同风险密度：房地产开发企业到位资金同比 -21.6%、国内贷款 -33.1%（`客户画像.md` §4.1 第 138 行，国家统计局原文），意味着账期拉长、票据结算、以房抵款等条款增多，合同评审（法务+财务）负荷随之上升（§4.1 第 145 行、§4.3 表格第 159 行）。同时客户结构为央国企总包与战略客户（§1.4 第 64–67 行），【推断】对应"框架协议 + 集采订单 + 项目合同"多层合同结构，版本多样性高（§5.1 第 172 行）。
- **为何难**：①法务团队人数、审核层级与时限、标准模板数量**均未检索到公开来源**（§5.1 第 181 行），"人少事多"目前只是推断而非已证事实；②合同审阅不是单点判断，而是"逐条对照公司立场"——哪些必须改、哪些可让、哪些是红线，规则在资深法务脑中；③多法人主体下同一份框架协议可能存在多个签署主体版本（§2.1 第 83 行【推断】）。
- **谁痛**：法务负责人（瓶颈与背锅位）；商务/销售（等审就意味着丢单风险）；财务（账期与收款条款）。
- **能否拆成多智能体岗位协作**：**可以，且这是全篇最贴合"多智能体协作"的一条**。对照 `行业案例.md` 案例 1（Harvey，C 级）：主办 agent 拆活 + 按 playbook 规则并行起子 agent + 分支修改 + 冲突升级给主办裁决 + 逐条结论挂原文（§2 案例 1 第 44–50 行）。可直接映射为"合同官（总分派）+ 商务条款官 + 质量/质保条款官 + 资质合规官 + 用印要件官"（§5.1 第 219 行）。用 `行业案例.md` §3 的四问自检：①多岗位角色分工 ✔ ②有交接物（结构化结论+原文位置）✔ ③有冲突升级且人拍板 ✔ ④写回业务系统并留痕 ✔——四问全"是"，属**强对齐**。
- **不宜硬上的边界**：①**agent 不出法律意见、不做定责**，只做"偏离识别 + 建议 + 依据"；②不得照搬 Harvey 的 77%/87%（§5.3 第 238 行：依赖自建评测集与内部律师标注，该前提在本客户不存在）；③必须先有 playbook 与标注集，否则并行 agent 只会把口径分歧放大到更多条款（§6 第 250 行）。
- **依据**：`客户画像.md` §1.4（第 64–67 行）、§2.1（第 83 行）、§4.1（第 138、145 行）、§4.3（第 159 行）、§5.1（第 172、181 行）；`行业案例.md` §2 案例 1（第 40–73 行）、§3（第 189–196 行）、§5.1（第 215–223 行）、§5.3 第 1 条（第 238 行）、§6 第 1 条（第 250 行）。

#### P3 多法人多区域：模板、授权、用印口径天然分散

- **现状**：【事实】下辖陕西、江苏、兰州、北京、上海、山东等多家全资子公司，覆盖陕西、北京、上海、河南、河北、山东、山西、江苏、浙江、安徽、湖北、广州、深圳、成都、重庆、南宁等重点市场（`客户画像.md` §2.1 第 82 行，原文列举）。【推断】"同一套销售政策、报价与合同模板要在多法人、多区域间复用；跨主体审批与用印是天然的管理难点"（§2.1 第 83 行，原文推断）。
- **为何难**：①签约主体选错会直接影响回款与诉讼管辖；②用印/授权规则**未检索到公开来源**（§5.1 第 181 行），无法判断是"总部集中印控"还是"区域授权"；③2018 年泛微协同 OA 若仍在用，可能承载合同/用印审批流，但"版本、覆盖范围、是否与业务系统打通均未知"（§3.1 第 105–106 行，二手+推断）。
- **谁痛**：法务与印章管理员（合规责任）；区域负责人（跑签成本）；财务（主体与账户一致性）。
- **能否拆成多智能体岗位协作**：**部分适合**。"签约主体与资质要件核对""模板版本比对""用印要件齐备性检查"可做成独立岗位 agent，输出"缺什么、找谁、依据哪条"；**但授权授予与用印批准必须留在人**（且很可能留在既有 OA 审批流内，而非新系统）。
- **不宜硬上的边界**：不要在未确认现有 OA/用印流程前设计"新审批链"，否则是替换而非叠加，落地阻力与合规风险同时上升（§7 待核 5/6 第 230–231 行）。
- **依据**：`客户画像.md` §2.1（第 82–83 行）、§3.1（第 105–106 行）、§5.1（第 181 行）、§7 待核 5/6（第 230–231 行）。

#### P4 审查过程与结论不留痕，事后无法回溯"当时为什么这么改"

- **现状**：【推断】上游未见任何 CLM、审阅留痕或版本管理工具的公开线索（`客户画像.md` §5.1 第 183 行），仅见 2018 年协同 OA 合作（§3.1 第 105 行，二手待核）。若审查仍以"邮件 + Word 批注 + 口头沟通"为主，则条款级判断理由不可复用。
- **为何难**：留痕不是"存个文件"，而是"每条风险 → 对应条款原文 → 依据哪条 playbook → 谁批准了例外"。这要求结构化，而非文档堆叠。行业侧同构证据：案例 1 明确把"分类、所选立场、改动摘要、理由"随审阅存档，用户追问时复用而不整链重跑（`行业案例.md` §2 案例 1 第 49 行）。
- **谁痛**：法务（被追问时无法自证）；内控/审计（挂牌后披露义务增强，见 §3.3 第 123 行【推断】）；销售（历史条款无法复用，每单重谈）。
- **能否拆成多智能体岗位协作**：**适合**，且是自动化的**副产品而非额外工程**——只要每个 agent 的结论都强制带"原文位置 + 规则编号 + 置信度"，审计链自然成立（`行业案例.md` 案例 1「对齐点」第 67 行；§5.1 第 220 行）。
- **不宜硬上的边界**：可追溯 ≠ 可定责。留痕只能证明"当时依据什么判断"，不能替代法律责任的归属认定。
- **依据**：`客户画像.md` §3.1（第 105 行）、§3.3（第 123 行）、§5.1（第 183 行）；`行业案例.md` §2 案例 1（第 49、67 行）、§5.1（第 220 行）。

#### P5 合同数据敏感，跨主体可见性与部署形态未定

- **现状**：【待核】是否有明文的数据安全/等保/信创要求，上游明确未覆盖（`客户画像.md` §7 待核 12 第 237 行）。合同含客户名单、价格、账期、违约责任，属企业最敏感数据之一；且集团为多法人结构（§2.1 第 82 行），"哪一级法务能看哪一级合同"本身没有公开口径。
- **为何难**：合同审查天然需要"全集团口径统一"（同一 playbook），但数据权限又必须"按主体隔离"，两者方向相反；再叠加外部模型调用，会触发客户对数据出域的顾虑。
- **谁痛**：IT/合规（否决权握在手上）；法务（拿不到全量数据就无法统一口径）。
- **适配结论**：**这是约束项，不是可自动化对象**。它决定后面所有方案的部署形态与接入方式，必须先问清再设计。
- **依据**：`客户画像.md` §2.1（第 82 行）、§7 待核 12（第 237 行）；`行业案例.md` §6 第 1 条（第 250 行，数据一致性优先）。

### B 组｜场景二：销售人员能力参差，需要销售助手/专家

#### P6 能力参差已被制度承认：讲标与标书生产高度依赖个人

- **现状**：【事实】2026-05-15/16 举办"2026 年度'五星评定'通关活动"，流程为"自我介绍 → 个人经典案例复盘 → **现场讲标呈现** → 评委综合点评"，明确"重点检验其大客户与大项目的开发能力"；**经理级还需完成"销售政策制度管理笔试"**（`客户画像.md` §5.2 第 187 行，官网新闻）。
- **为何难**：【推断】①"讲标"被设为通关核心动作，说明标书/方案生产是高频高耗环节（§5.2 第 188 行）；②能力差异被"五星分级 + 通关"显性化，反过来说明**未通关者的产出质量确有落差**；③标书依赖个人经验与历史案例，而"标书库、案例库、话术库、培训 LMS 的建设情况"**未检索到公开来源**（§5.2 第 191 行）——素材很可能散落在个人电脑与微信里。
- **谁痛**：一线销售（写标书熬夜、讲标没底）；区域负责人（大项目靠少数王牌）；销售管理部（培训投入无法沉淀为组织能力）；市场/技术（被反复索要同一批素材）。
- **能否拆成多智能体岗位协作**：**适合**。可拆为"需求解析（读招标文件/评分办法）→ 资质与业绩匹配（从案例库取证的岗位）→ 技术方案段落起草（按产品线）→ 商务条款与偏离表核对 → 合规与一致性校验（禁虚构业绩、禁超授权承诺）"，最后由人定稿与讲标。对照 `行业案例.md` 案例 3（Schneider，B 级）：制造业 B2B、销售人数多、跨区域，是**最接近的公开样本**，其关键不是"会聊天"而是"把结果写回系统"（§2 案例 3 第 116–117 行）；案例 4（KPN，B 级）提供"RFP 长文档摘要 → 报价草案"的近似环节与"小样本 + 周节省小时"的验收口径（§2 案例 4 第 133、141 行）。
- **不宜硬上的边界**：①**业绩、资质、荣誉不得由 agent 生成或推断**——官网"7 大工厂 vs 6 个基地"的口径差异（§1.3 第 59 行【待核】）就是现成反例，写进标书即对外风险；②演示/讲标的话术与现场应变属人的能力，agent 只能供料；③案例 3/4 均**不是多智能体**、也**不闭环**（§2 案例 3 第 120–122 行、案例 4 第 144–146 行），不可据此承诺"自动中标"。
- **依据**：`客户画像.md` §5.2（第 187–191 行）、§1.3（第 59 行）、§1.5（第 71–74 行）；`行业案例.md` §2 案例 3（第 100–123 行）、案例 4（第 127–147 行）、§5.2（第 225–234 行）。

#### P7 销售政策与制度「有文本、难查准、执行不一致」

- **现状**：【事实】经理级通关含"销售政策制度管理笔试"，并要求针对管理问题做剖析性汇报与整改计划（`客户画像.md` §5.2 第 187 行）。【推断】把"销售政策制度"设为**显性考核项**，说明①政策文本存在且有约束力；②执行偏差是管理层已知问题（§5.2 第 188 行，原文推断"政策查询与合规问答有明确使用场景"）。
- **为何难**：政策散落在制度文件、通知、区域补充规定中，且会随区域与时间变化；销售要的是"我这一单能不能这么报"，而制度给的是"原则性表述"。更麻烦的是：**报价审批流程本身未检索到公开来源**（§2.2 第 92 行），意味着"问谁、按什么批"在公开层面不可见。
- **谁痛**：一线销售（怕报错被驳）；区域商务（重复解答）；销售管理部（政策落地靠培训与检查）。
- **能否拆成多智能体岗位协作**：**部分适合**。"政策检索 + 引用原文 + 场景化解释 + 提示需审批"可做；但**政策的解释权与例外批准权必须在人**（销售管理/商务负责人）。对照 `行业案例.md` 案例 5（Salesforce，A 级）的失败教训：早期"不知道率"达 30%，靠单一事实源与清理过期页面降到 10% 以下（§2 案例 5 第 159 行）；且"把'不知道率/答非所问率'当质量指标，未达标不扩量"（§5.2 第 234 行）。本客户若政策文本未版本化，这个指标风险更高。
- **不宜硬上的边界**：**返利、账期授信、区域价格政策不得交给 LLM 自由裁量**——`行业案例.md` §5.3 第 3 条明确要求走规则引擎/额度表，agent 只做解释与异常提示，否则不可审计（第 240 行）。本客户的经销商/代理体系是否存在都尚未确认（`客户画像.md` §2.2 第 90–91 行、§7 待核 7 第 232 行），更不应预设其规则形态。
- **依据**：`客户画像.md` §2.2（第 90–92 行）、§5.2（第 187–188 行）、§7 待核 7（第 232 行）；`行业案例.md` §2 案例 5（第 159 行）、§5.2（第 234 行）、§5.3 第 3 条（第 240 行）。

#### P8 报价与让利依赖个人经验，agent 不宜介入定夺

- **现状**：【待核】报价审批、投标立项的内部流程文件属企业内部资料，"公开渠道通常不可得"（`客户画像.md` §2.2 第 92 行）。【推断】在集采压价、头部以规模压价的格局下（§4.2 第 151 行），报价是核心竞争手段，也是毛利守门环节。
- **为何难**：报价 = 成本 + 竞争态势 + 客户关系 + 战略取舍，其中至少三项无法从系统取数；且让利一旦错了，后果是直接亏损，不可"事后修正"。
- **谁痛**：报价/商务负责人（决策压力）；财务（毛利）；销售（等批复）。
- **适配结论**：**不宜硬上**。可做的是"取数与前置校验"（历史成交价区间、成本卡、授权额度是否越界、账期是否超限），**最终定价与让利由人拍板**。行业侧亦有明确提醒："agent 做到'初稿 + 风险提示 + 建议报价区间'，人做最终报价与让利"（`行业案例.md` §5.2 第 233 行）；且"不能把'法务轻触修改'标准套到销售报价"，二者质量函数相反（§5.3 第 2 条 第 239 行）。
- **依据**：`客户画像.md` §2.2（第 92 行）、§4.2（第 151 行）；`行业案例.md` §5.2（第 233 行）、§5.3 第 2 条（第 239 行）。

### 横切项

#### P9 数据底座不明：ERP/CRM/合同系统全部未覆盖

- **现状**：【事实】上游明确"ERP（品牌/模块/上线年份）、MES、WMS、CRM、SRM、PLM 等核心系统的选型与实施情况"**均未检索到公开来源**；数据中台、AI/大模型、RPA 或智能体实践同样未覆盖；IT/数字化团队人数与组织归属亦未知（`客户画像.md` §3.2 第 112–115 行）。
- **为何难**：多智能体协作的价值在于"跨环节交接"，而交接依赖系统接口与单一事实源。若 CRM 不存在，销售侧的"回写"就无处可写；若合同无系统承载，"写回"只能落在文件与 OA 流程里。`行业案例.md` §6 第 1 条把这一点列为硬约束："数据一致性优先于模型能力……否则多智能体只会把错误放大到更多环节"（第 250 行）。
- **谁痛**：IT（被要求接系统却没有系统可接）；业务（agent 结论无法落到日常入口，用两次就弃用）。
- **适配结论**：**前置约束**。这也是"先做合同链路、后做销售赋能"的重要理由之一——合同链路的落点（文件 + 审批流）比销售链路（CRM 回写）对系统依赖更低。
- **依据**：`客户画像.md` §3.2（第 112–115 行）、§7 待核 5/6（第 230–231 行）；`行业案例.md` §6 第 1 条（第 250 行）。

## 2. 适配度判断（分层）

### 2.1 适合用「多智能体协作把业务自动做起来」

判据不是"能不能用 AI"，而是 `行业案例.md` §3 的四问（第 189–196 行）：多岗位分工、有交接物、有冲突升级且人拍板、写回系统并留痕。四条同时成立才叫强对齐。

| 环节                               | 为什么适配                                                     | 岗位化拆法（建议，非定稿）                             | 人的位置             | 案例对照                       |
| ---------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------ | -------------------- | ------------------------------ |
| 合同到件 → 结构化 → 待审队列（P1） | 有唯一正确答案（以原件为准）、可交叉校验、错误可被差异清单暴露 | 收件/完整性 → 抽取 → 归一校验 → 缺件催办               | 只校差异与低置信字段 | 案例 2（形状同构，非多智能体） |
| 合同首轮条款审查（P2/P4）          | 有 playbook 可依、条款可切分、冲突可升级、结论天然要挂原文     | 合同官 + 商务条款 + 质保条款 + 资质合规 + 用印要件     | 法务终审、例外批准   | 案例 1（强对齐）               |
| 标书/讲标素材生产（P6）            | 素材有出处、可按评分办法拆解、虚构可被校验拦截                 | 招标解析 + 业绩匹配 + 技术段落 + 商务偏离 + 一致性校验 | 销售定稿、讲标本人   | 案例 3/4（部分对齐）           |

**共同特征**：都是"文档进 → 结构化判断出 → 有人签"，且判断标准可写成文字（playbook、评分办法、要件清单）。这正是多智能体分工能成立的前提——**规则可外化，才谈得上分派与裁决**。

### 2.2 部分适合（agent 供料，人定夺）

- **销售政策问答（P7）**：问答可自动，**解释权与例外批准不可**。验收应看"引用原文率 + 不知道率"，而非"回答得多顺"（`行业案例.md` §5.2 第 234 行）。
- **用印要件核对（P3）**：可核对"要件齐不齐"，不可决定"能不能盖"。
- **报价取数与越界提示（P8）**：可给区间与告警，不可定价。

### 2.3 不宜硬上（须明确排除，避免方案失真）

| 不宜自动化的内容                       | 理由                                                                                 | 依据                                                                                                  |
| -------------------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 出具法律意见、认定合同责任             | 法律定责属执业资质与法人责任范畴，agent 无主体资格；错一次即实质损失                 | `客户画像.md` §5.1（第 181 行，法务职能真实存在且非空转）；`行业案例.md` 案例 1（人做终审，第 66 行） |
| 用印批准与授权授予                     | 属公司治理权限，不可外包给模型；且现有审批流可能已在 OA 内                           | `客户画像.md` §3.1（第 105 行）、§7 待核 6（第 231 行）                                               |
| 最终报价与让利                         | 主观商业判断，含竞争与关系变量，无法从系统取数                                       | P8；`行业案例.md` §5.3 第 2 条（第 239 行）                                                           |
| 经销返利 / 账期授信 / 区域价格政策测算 | 强规则，必须可审计；LLM 自由裁量不可接受                                             | `行业案例.md` §5.3 第 3 条（第 240 行）；客户体系本身待核（`客户画像.md` §7 待核 7）                  |
| 客户关系维护与高价值谈判               | 案例 5 明确人机分工：agent 做量大重复的活，人做关系与复杂成交                        | `行业案例.md` §2 案例 5（第 158 行）                                                                  |
| 替换 CRM/ERP 的重系统建设              | 上游对现有系统一无所知，谈替换即无依据；且基础层挂牌、融资能力有限，倾向轻量分期投入 | `客户画像.md` §3.2（第 112–115 行）、§3.3（第 123 行【推断】）                                        |
| 以"多 agent"为卖点的空壳编排           | 无共享上下文、无交接物、无冲突升级、无写回，只是多个 bot                             | `行业案例.md` §3（第 187 行）、§5.3 第 7 条（第 244 行）                                              |

### 2.4 一条必须说清的话

`行业案例.md` §1 的结论是：**"多智能体协作 + 人在环审批 + 全程可追溯"的建材行业公开样本，本次未检索到**（第 34 行）；国内防水/建材一体化落地、经销渠道多智能体赋能、合同 OCR→审查→用印全链路，均未找到可核验的一手案例（§4 第 204–207 行）。因此本客户的适配判断**建立在形状推理上，不是建立在同行已验证的结果上**——这一点在对外沟通时必须说明，不能包装成"行业已验证"。

## 3. 痛点排序（频次 × 影响 × 可自动化程度）

### 3.1 排序结果

| 优先级 | 痛点                      | 频次           | 影响 | 可自动化 | 排序理由                                                                                                                                                        |
| ------ | ------------------------- | -------------- | ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1**  | P2 合同首轮审查 + P4 留痕 | 待核（推断高） | 高   | 中高     | 影响最大且判断标准可外化；四问全过，是多智能体唯一"强对齐"的落点。频次虽无基线，但央国企集采 + 多法人结构使"版本多、条款密"成立（`客户画像.md` §5.1 第 172 行） |
| **2**  | P1 照片/扫描件结构化      | 高（推断）     | 中   | 高       | 它是 P2 的**前置**：不解决录入，审查 agent 拿不到可用输入。单独看影响中等，放在链路上是必经环节；且正确性可验证（对原件）                                       |
| **3**  | P6 标书/讲标素材          | 高（推断）     | 高   | 中高     | 影响直连订单，且"五星评定 + 讲标"证明组织已承认能力落差（§5.2 第 187 行）；但素材库若不存在需先建库，前置工作量被低估的风险大                                   |
| **4**  | P3 多法人模板/用印口径    | 高（推断）     | 高   | 中       | 影响高（合规与回款），但可自动化部分受限于现有 OA 未知，需先摸流程；不宜作为首个切口                                                                            |
| **5**  | P7 政策问答               | 中高（推断）   | 中   | 高       | 技术上最容易做，但价值上限受"政策文本是否已版本化"约束；且做小了像聊天机器人，做大了越权                                                                        |
| **6**  | P8 报价                   | 待核           | 高   | 低       | 影响最高但可自动化最低；只能做取数与告警，单独立项产出薄                                                                                                        |
| **7**  | P5 / P9 数据与合规约束    | —              | 高   | 低       | 不是"做不做"的问题，而是"必须先答"的问题；排最后是因为它不产生交付物，但**答不清就不能开工**                                                                    |

> 说明：本排序**不含效益测算**（属方案架构师职责）；"频次/影响"均为定性与推断，无客户基线支撑，见 §5 待核 2/3/10。

### 3.2 排序依据的三条逻辑

1. **先修"进料口"，再修"判断口"**：P1 不解决，P2 的输入质量不可控；但 P1 单独价值有限，故与 P2 同批推进、以 P2 为主叙事。
2. **优先选"判断标准已写成文字"的环节**：合同有 playbook 可依、标书有评分办法可依，这类环节才谈得上"分工 + 裁决 + 留痕"；报价没有可外化标准，故排后。
3. **系统依赖度反序**：合同链路可落在"文件 + 审批流"上，销售链路要求 CRM 回写——而 CRM 是否存在完全未知（§3.2 第 112 行）。在系统清单确认前，**合同链路是风险更低的起点**。
