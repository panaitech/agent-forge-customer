# 解决方案：雨中情「合同智能 + 销售知识库」Agent Forge 落地方案（草案）

> 版本：第 3 波交付稿｜依据：《痛点分析.md》及其上游《客户画像.md》《行业案例.md》
> 使用边界：本文为方案草案，**不含任何已签约、已上线、已验收的表述**；文中效益数字全部是标注口径的假设，**未经验证**；产品功能细节凡未在能力锚点内列明的，一律标「需产品确认」。
> 事实口径：客户流程与系统事实来自访谈转述（《痛点分析.md》标 `[访谈]`，D 级）；公开侧仅"有信息化历程、有官网运营"可证。文中引用的行业案例均为**外部案例**，只作机制参照，不构成雨中情可获得的收益。

## 一、主叙事

**面向企业的多智能体协作，在运行时上把业务自动做起来。**

> 官网内核：面向企业 · 多智能体协作 · 业务自动化。以下所有内容都是这一句在本案的展开，不另立口号。

这句话在本案里不是"再上一个 AI 助手"，而是三层含义：

1. **面向企业**：不是个人聊天工具，而是把合同、知识这两条"有单据、有规则、有人签"的链路装进可管控的企业运行时；权限、审批、审计是默认配置。
2. **多智能体协作**：一条链路拆成多个岗位型 agent（要素提取、清单匹配、结算校验、条款风险、知识萃取、质检仲裁），各管一段、各出结构化结果、按协议交接；不是让一个大模型读完合同直接给结论。
3. **在运行时上把业务自动做起来**：自动发生在真实系统与流程里——读销售易的结构化表单、比对报价单与产品清单、生成评审卡片、在企微答销售提问；每个写回点都过人工闸门、留痕可查。

需要明确：**造、跑、治理、观测不是对外的第二句口号**，而是"怎么做到这句话"的四类能力与工作方式，具体形态在第五节展开。主叙事只有上面这一句。

## 二、业务蓝图：双主线、一个知识底座、一道审批闸门

### 2.1 先直接回答：哪些业务、哪些岗位型 agent、谁审批、怎么验收

| 业务          | 协作的岗位型 agent                                     | 谁审批                                | 如何验收                                                         |
| ------------- | ------------------------------------------------------ | ------------------------------------- | ---------------------------------------------------------------- |
| 合同创建录入  | 合同受理主管（编排）＋要素提取、产品清单匹配、缺件追问 | 销售本人确认字段；区域商务复核        | 字段抽取准确率、清单 Top-3 命中率、单份录入耗时、人工改字段数    |
| 区域初审      | 三单比对、结算规则校验、评审卡片汇总                   | 区域商务专员逐单终审                  | 规则项校验通过率、漏检率（抽样）、单日处理量、退回原因归类准确率 |
| 商务/法务评审 | 条款抽取、标准条款比对、类案检索、风险分级、卡片汇总   | 商务按授权审批；**法务终审并定责**    | 风险条款召回率、引用可溯源率、法务采纳率、误报率                 |
| 知识生产      | 采集归集、知识萃取、质检（重复/冲突/时效/缺引用）      | 领域知识责任人**发布签核**            | 条目结构完整率、质检问题关闭率、发布退回率                       |
| 知识消费      | 检索—重排—作答—引用校验；销售教练（简报/案例推荐）     | 销售本人判断；不自动写回 CRM 关键字段 | 评测集准确率、引用正确率、拒答正确率、首次解决率                 |
| 质检仲裁      | 跨链路质检与冲突仲裁                                   | 质量负责人复核仲裁结论                | 仲裁一致率、争议条目闭环率                                       |

### 2.2 双主线怎么互相喂养

- **合同智能主线**：面向销售、区域商务、法务，解决"录得慢、审得粗、风险后置"；**知识库主线**面向全体销售与知识责任人，解决"存量乱、萃取难、问答不可信"。
- **共享知识底座**：物料名称映射表、标准条款库与风险标签、产品与报价口径、客户与项目主数据、案例卡、历史退回原因。两条线读同一套检索与引用机制，避免"合同一套叫法、知识库另一套"。
- **共享审批闸门与回路**：凡写回业务系统（合同字段、卡片结论、知识正式库）一律人工确认，agent 只出建议与依据；合同评审沉淀的条款风险反哺知识库，知识库的条款与案例又成为条款审查的比对依据——这条回路是两条线合并建设、而非两个孤立 PoC 的主要理由。

## 三、多智能体协作设计

### 3.1 岗位、输入输出与系统边界

协作模式：**合同链路用 supervisor**（受理主管分派、汇总、升级，抽取与清单匹配可并行，校验与条款串行）；**知识链路用 pipeline**（采集→萃取→质检→入库），质检/仲裁为跨链路旁路，不阻塞主流程。

| 岗位 agent                 | 输入                                   | 输出（结构化）                                                  | 工具/系统边界                                |
| -------------------------- | -------------------------------------- | --------------------------------------------------------------- | -------------------------------------------- |
| 合同受理主管（supervisor） | 新建合同任务、单据号、客户与商机上下文 | 任务分派、缺件清单、汇总卡片、升级请求                          | 只编排与汇总，不直接改单据                   |
| 要素提取                   | 合同文本/表单、报价单、产品清单        | 字段值＋置信度＋原文出处（页码/段落/单元格）                    | 只读文档与表单；不写库                       |
| 产品清单匹配               | 报价单行项、合同行项、物料映射表       | 一对多/多对多匹配建议、未匹配项、候选 Top-3                     | 只读映射表；映射口径由客户主数据责任人定     |
| 结算规则校验               | 付款比例、账期、金额、收货与签收信息   | 规则逐条通过/不通过＋差异值                                     | **数值一律用规则引擎复算**，模型只抽取不复算 |
| 条款风险审查               | 合同条款、标准条款库、类案与历史退回   | 命中条款类型、原文引用、风险级别建议、缺失条款提示              | 只读条款库；**不输出"可签/不可签"**，不定责  |
| 知识萃取                   | 复盘记录、讲标材料、答疑记录、文档     | 结构化条目：编号/类型/标题/适用场景/销售阶段/内容/索引出处/标签 | 只写草稿区，不直接入正式库                   |
| 质检/仲裁                  | 各岗位输出、知识草稿、历史冲突记录     | 质检报告、冲突判定建议、需人工裁决清单                          | 无发布权、无审批权                           |
| 销售教练                   | 客户/商机上下文、知识库、历史案例      | 拜访简报、异议应对话术、可复用案例                              | 只读；建议不自动写入 CRM 关键字段            |
| 问答                       | 用户问题、权限上下文、知识库           | 答案＋引用条目＋可信度；不足则拒答                              | **检索前按权限过滤**，越权内容不进入上下文   |

### 3.2 交接协议

所有交接走统一信封，缺一项即视为交付不合格、退回上游重做：

```
task_id / 单据号 / 岗位 / 结论类型
items[]: { 字段或条款, 值或判定, 置信度, 出处, 校验结果 }
unresolved[]: { 项目, 原因, 建议追问对象 }
next: 建议下一岗位 / 建议人工动作
```

三条硬规则：①**无出处不成立**——任何字段与条款结论必须能回指原文位置；②**缺字段追问、不猜**——缺失或冲突进 `unresolved`，由受理主管向销售发起追问；③**幂等与可重跑**——单个岗位失败只重跑该岗位，不整链重来。

### 3.3 置信度与升级人工

| 情形                        | 处理                                                                       |
| --------------------------- | -------------------------------------------------------------------------- |
| 置信度 ≥0.90 且规则校验通过 | 进入"建议采纳"，**首期仍逐单人工确认**；稳定后可抽样复核（需客户书面同意） |
| 0.70–0.90                   | 标"待核"，进评审卡片"需人工判断"区，不自动填                               |
| <0.70、字段冲突、无出处     | **拒答/挂起**，升级人工，不写回                                            |
| 条款命中高风险类型          | 强制升级法务，卡片只给原文与比对依据                                       |
| 任一写回动作                | 一律 HITL 人工确认，记录确认人、时间、修改内容                             |

### 3.4 为什么必须是多智能体，而不是一个大模型一次做完

- **错误可定位、可重跑**：合同动辄数十字段、清单多对多。一次性生成把"抽取、比对、判断、汇总"混在一个输出里，错了不知错在哪、也无法只重跑那段。
- **可校验**：拆开后每段可过 schema 与规则引擎；金额、付款比例必须复算，不能由模型"读出来就算完"。
- **可分工分权、可审计**：条款判断所需的知识与权限不同于字段抽取，不同岗位挂不同知识域与工具；审计要回答"数字从哪来、谁改的、依据哪条规则"，只有分段留痕才能逐项溯源。
- **上下文可控**：长合同＋长清单＋条款库一次塞入会显著漏项。

反向边界同样明确：**agent 不是越多越好**。本方案合同 6 岗、知识 5 岗已接近协调成本上限。技术评审、变更/补充协议、销售陪练暂不进入多智能体设计（见《痛点分析.md》§一.3、§一.7、§五）。

## 四、业务自动化流程与人工闸门

### 4.1 合同：创建 → 初审 → 商务/法务 → 终审 → 归档

| 步骤             | 自动完成                                                                                       | 人工闸门                                   |
| ---------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------ |
| ① 创建           | 解析报价单与附件、预填结构化表单、清单映射建议、缺件追问                                       | **G1**：销售逐项确认后提交（首期全量确认） |
| ② 初审           | 三单比对（报价/合同/清单）、结算规则与付款比例 100% 校验、收货信息与签收单一致性、生成评审卡片 | **G2**：区域商务专员终审，卡片只作辅助     |
| ③ 商务评审       | 授权额度预判（仅提示，不决定）、缺件检查、退回原因归类                                         | **G3**：商务按授权审批，超权限上集团商务   |
| ④ 法务评审       | 条款抽取、标准条款比对、缺失条款提示、类案检索、风险分级                                       | **G4**：法务终审并定责；高风险强制人工     |
| ⑤ 用印/建单/归档 | 审查结论与用印、建单的闸门联动（**属流程集成，非 agent 决策**）                                | **G5**：用印审批人；未过审不发起用印       |

### 4.2 知识：采集 → 萃取 → 质检 → 入库 → 问答 → 反馈迭代

| 步骤       | 自动完成                                        | 人工闸门                                         |
| ---------- | ----------------------------------------------- | ------------------------------------------------ |
| ① 采集     | 多源归集（销售易/OA）、去重、来源登记、密级初判 | —                                                |
| ② 萃取     | 文档/复盘/讲标 → 结构化条目草稿（八字段）       | **K1**：领域知识责任人补全与署名                 |
| ③ 质检     | 重复、冲突、时效过期、引用缺失、口径不一致检测  | **K2**：质量负责人关闭质检问题                   |
| ④ 入库     | 按三级权限落库、建索引、版本登记                | **K3**：**发布签核**后方入正式库；旧版降级不删除 |
| ⑤ 问答     | 权限过滤→检索→重排→作答→引用校验→不足则拒答     | 销售自行判断；争议答案可一键报错                 |
| ⑥ 反馈迭代 | 无答案/差评聚类、缺口清单、待补条目建议         | **K4**：知识责任人认领并更新，回到 ②             |

### 4.3 不可自动化边界（写死在方案里）

法务定责与签署、用印与建单的审批权、权限模型与密级定义、物料主数据治理归属、考核与绩效执行、对外价格与账期承诺、资信授信决定——**均不交给 agent**。这些或是制度问题、或是责任问题，agent 只能提供依据与提示；把它们当交付物是这类项目最常见的失败原因（《痛点分析.md》§四）。

## 五、怎么工作：把上面这条链路造出来、跑起来、管住、看得见

> 以下为能力与工作方式说明；涉及控制台具体字段、接口协议、版本边界的，均标「需产品确认」。

**5.1 怎么造——把业务配成岗位。** 以"角色 + 能力 + 触发器 + 会话"四要素定义岗位：角色写职责与禁止项（如条款 agent 禁止给签署结论），能力挂工具与知识域，触发器接"新建合同""知识草稿提交""企微提问"等事件，会话承载多轮追问与人工插入。产物是一份业务方看得懂、能改的岗位说明书。**需产品确认**：岗位模板的导入导出与版本管理形态。

**5.2 怎么跑——运行时 + MCP/Skill。** 运行时负责调度、状态、重试与交接；MCP 接销售易、OA、企微、文档存储与规则引擎；Skill 承载"结算校验规则""条款比对口径""条目八字段模板"等作业标准。工具调用有白名单与入参校验，只读为主，写操作走审批。**需产品确认**：连接器清单、是否支持自建 MCP、内网调用方式。

**5.3 怎么治理——权限事先定好。** RBAC 按角色（销售/区域商务/法务/知识责任人/知识管理员/审计只读）× 密级（全员/区域/机密）授权，检索前过滤；HITL 覆盖全部写回点；审计按运行粒度留痕；熔断按错误率、拒答率、投诉量设阈值，触发即降级纯人工。多租户写、他人 HITL、审计验真属**企业版**能力，需钥匙解锁；社区版可自托管满足单租户 PoC，边界**需产品确认**。

**5.4 怎么观测——做完能查到每一步。** 一次运行可回看：触发源、读到的单据与字段、工具调用与返回、各岗位输出与置信度、人工决定与用时、写回回执；周报看采纳率、拒答率、退回原因与无答案聚类。审计导出与哈希链验真的企业版形态**需产品确认**。

**5.5 部署形态——自托管。** 部署于客户机房或专有云，合同、报价、客户材料不出域；服务方签 NDA，合同原件不进服务方电脑，调试只用脱敏样本。若走外部模型通道须单独评估数据条款；是否支持完全离线模型与内网全链路，**需产品确认**。

## 六、POC 切口（3 个）

**POC-1 合同创建自动填单与要素提取（首选，4–6 周）**

- 范围：单一合同类型（建议先做占比最高的经销或直供合同）、单一区域；只做"预填 + 清单匹配 + 缺件追问"，不做审批。
- 集成：销售易合同模块结构化表单（Java 二次开发，**接口能力待核**）；报价单以附件/导出文件进入；写回仅限草稿字段并经 G1 确认。
- 验收指标（目标值，须先测基线）：字段抽取准确率、清单匹配 Top-3 命中率、缺字段召回率、单份人工耗时、人工改字段数、误填导致的退回数（应为 0 容忍）。
- 前置：历史合同与模板抽样 50–100 份、物料映射表口径由客户定、报价单可机读、现测 30 分钟/单基线。

**POC-2 商务/法务评审辅助卡片（4–6 周，建议在 POC-1 后串行）**

- 范围：三单比对 + 结算规则校验 + 条款风险卡片；**不给审批结论、不做定责**；先覆盖 20–30 条高频规则与 30–50 条标准条款。
- 集成：读取合同与报价数据、条款库（初期可用文档库替代）、输出卡片到 OA 或合同审批页侧栏（**需产品确认**嵌入方式）。
- 验收指标：规则校验项覆盖率、漏检率（法务抽样复核）、风险条款召回率、引用可溯源率、法务采纳率、误报率、卡片生成时延。
- 前置：审批流可读接口、标准条款库与历史退回原因整理、法务参与定义"必查项"。

**POC-3 销售高频知识域问答（可与 POC-1 并行，4–6 周）**

- 范围：选 1–2 个高频域（如产品选型/施工工艺、报价与结算口径），先做几百条；只做问答与引用，不做全量知识治理。
- 集成：企微作为唯一入口（现有机器人效果差 `[访谈]`，改造面小）；知识源接 OA 与销售易知识库；按三级权限过滤。
- 验收指标：30–50 题评测集准确率、引用正确率、拒答正确率（该拒答时必须拒答）、首次解决率、平均取答案时长、越权命中数（应为 0）。
- 前置：三级权限与密级清单由客户安全口径定、每个域指定知识责任人与发布签核人、企微与知识库接口确认。**"几百条覆盖约 80% 常见问题"是客户侧判断，须用评测集验证，不作为承诺。**

## 七、效益假设（三档，全部为假设）

> 统一声明：**以下均未经验证，需 POC 基线测量**；不含建设、标注、审核与运营成本；不折算金额（缺薪酬数据）；不得对外作为承诺或 ROI 引用。基线替换访谈口径前，仅用于判断"值不值得做"，不用于立项测算。

| 口径                       | 保守         | 基准         | 进取         | 关键假设                                                                   |
| -------------------------- | ------------ | ------------ | ------------ | -------------------------------------------------------------------------- |
| 单份合同创建耗时           | 30 → 24 分钟 | 30 → 18 分钟 | 30 → 12 分钟 | 50%/70%/85% 字段可预填；人工复核仍需 8–12 分钟；报价单可机读；映射表已统一 |
| 每 1000 份合同节省录入工时 | 100 小时     | 200 小时     | 300 小时     | 按上档耗时差直算（6/12/18 分钟 ×1000）                                     |
| 区域初审人均日处理量       | 50 → 65 单   | 50 → 80 单   | 50 → 110 单  | 40%/60%/75% 检查项由机器预检；**人工仍逐单签**；退回率不升                 |
| 每 1000 份合同所需初审人日 | 20 → 15.4    | 20 → 12.5    | 20 → 9.1     | 按上档处理量直算，节省 4.6/7.5/10.9 人日                                   |

| 高频域问题覆盖率           | 不做假设     | 不做假设     | 不做假设     | 客户判断"约 80%"须评测集验证                                               |

明确不写的三件事：不写"审核从数天缩到数小时"（缺环节时长基线）、不写"50→200 单/天"（客户预期，非本方案假设）、不写投资回收期。文中提到的"审查辅助＋法务终审""按角色分权＋审核后发布""回答附引用"等机制，均来自**外部公开案例**（证据级别 C–D，非本客户案例），只作设计参照，不作为雨中情的收益依据。

## 八、治理与安全

- **权限分级**：三级密级（全员/区域/机密）× 角色 RBAC，检索前过滤，越权内容不进入上下文；机密域仅白名单岗位可见；agent 服务账号与个人账号分离，操作可归属到人。
- **数据不出域**：自托管于客户侧，合同与客户材料不出客户环境；服务方不接触原件，只用脱敏样本，签署 NDA 与数据处理条款。
- **不确定就拒答**：低于阈值、无引用、跨权限、超出知识域时**明确拒答并给出求助对象**，不允许"编一个像样的答案"；拒答率是健康指标而非故障。
- **审计留痕**：全链路运行记录＋人工确认记录＋写回回执，可按单据号、时间、岗位、人检索，保留期按客户合规要求定。
- **灰度与终审**：新旧流程并行不少于 4 周，**以旧流程出单为准**逐单比对差异，达标才谈扩面，出现严重错误即回退纯人工；合同签署、法务定责、知识发布、用印建单为四处不可绕过的硬闸门。
- **熔断**：错误率／投诉／越权告警触发自动停用对应岗位，不影响既有流程。

## 九、风险与应对

| 风险                             | 影响                                 | 应对                                                                     |
| -------------------------------- | ------------------------------------ | ------------------------------------------------------------------------ |
| 物料名称不统一、映射表无人负责   | 清单匹配准确率上不去，POC-1 直接失败 | 把主数据治理列为前置条件与客户责任，先做小范围映射表，不承诺全量自动匹配 |
| 销售易/OA/企微接口不可读或不可写 | 只能做"人工上传"的降级形态           | 0–4 周先做接口勘察，接口不通则改 POC 范围或顺序                          |
| 抽取幻觉与条款误判               | 错误流入合同，风险放大               | 无出处不成立、数值规则复算、条款只提示不定责、首期逐单人工确认           |
| 用户不用、仍问人                 | 效益归零                             | 入口放在企微与合同页内、答案带出处、知识责任人署名、纳入周会看采纳率     |
| 知识责任人不明确                 | 萃取与发布停摆                       | 每个域书面指定责任人，发布签核为强制流程                                 |
| 权限过宽泄密 / 过严不用          | 合规风险或使用率低                   | 三级权限先严后松，按岗位灰度开放，越权命中数作为红线指标                 |
| 效益不达预期                     | 项目被质疑                           | 立项即约定基线测量方法与三档口径，对外只讲假设                           |
| 组织与考核冲突（如按单量考核）   | 消极抵触                             | 明确 AI 不改变考核口径，减负不减编；先在愿意试的区域做                   |

## 十、实施路线

- **0–4 周｜打地基**：现测基线（录入 30 分钟、初审时长与单量、退回率）；接口勘察（销售易/OA/合同/印章/企微）；脱敏样本与合同模板抽样；物料映射表口径；三级权限与密级清单；30–50 题评测集；POC-1 立项与验收口径签字。
- **1–3 月｜两个 PoC 并行**：POC-1 合同创建自动填单 + POC-3 高频知识问答；企微入口改造；灰度双线并行；周度看采纳率、拒答率、差异率；POC-1 达标后启动 POC-2 条款卡片的数据准备。
- **3–6 月｜扩面与治理**：POC-2 商务/法务卡片上线；知识域从 1–2 个扩到 3–5 个；RBAC、熔断、审计报表正式启用；形成岗位说明书与运营 SOP；按实测数据重算三档效益，决定是否推广到更多区域。

## 十一、待核清单

1. 销售团队规模、区域数量、合同审核岗位编制（D 级）。

**一句话收束**：这条方案不承诺"AI 替人签合同"，只承诺把合同与知识两链路上"有规则、有单据、有人终审"的中间段，用多智能体协作在运行时自动跑起来——人保留判断与签署，机器承担比对、抽取、汇总与留痕。
